# 제출과 검증

> [리더보드로](../leaderboard.md)

---

**클라이언트는 점수를 보내지 않습니다. 리플레이를 보냅니다.** 서버가 같은 코어로 다시 돌려
지표를 세고, 그것만 순위표에 오릅니다. 대조 게이트를 위해 만든 결정론이 여기서 두 번째로
쓰입니다.

## 랭크 시드

|무엇|어떻게|
|--|--|
|발급|`POST /ranked/seed { deck, stake, pool }` 또는 `{ challenge }` → `{ seed, expiresAt }`. 로그인이 필요합니다|
|모양|`CLOVER-` 뒤 무작위 8자. 지금 시드와 같은 자리에 들어갑니다|
|수명|**24시간 안에 시작 · 한 번만 제출**|
|묶임|계정 · 덱 · 스테이크 · 풀 · 챌린지. **발급받은 설정과 다르게 시작한 런은 오르지 않습니다**|
|챌린지|`challenge` 를 주면 **덱 · 스테이크 · 풀을 받지 않습니다.** 챌린지가 셋을 다 정하므로 함께 오면 `400` 입니다 — 무시하고 덮으면 클라이언트가 무엇으로 시작하는지 모르는 채로 시작합니다|
|한도|계정당 시간에 20개. 안 쓴 시드는 그냥 만료됩니다|

**시드를 서버가 주는 것이 검증의 반입니다.** 시드를 고르게 두면 좋은 시드를 오프라인에서
찾아 오는 것이 가능하고, 그것은 실력이 아니라 계산입니다. 시드를 한 번만 쓸 수 있게 두면
같은 런을 두 번 올리는 것도 함께 막힙니다.

**자기 시드의 런은 그대로 놀 수 있습니다.** 시드 입력 칸은 남고, 다만 그 런은 끝나도 순위에
가지 않습니다. 시작할 때 화면에 「랭크」 표지가 있고 없고로 갈립니다 —
[화면](screens.md#랭크-표지).

## 제출

```
POST /runs
{
  seed, deck, stake, pools,          // 랭크 시드 발급 때의 것과 같아야 합니다
  challenge,                         // 챌린지가 아니면 "". RunState 의 것을 그대로
  actions: Action[],                 // 처음부터 끝까지
  fingerprint: string,               // 클라이언트의 규칙 지문
  claimed: Metrics                   // 클라이언트가 센 지표. 참고용
}
→ 202 { submissionId }
```

**`challenge` 는 `pools` 와 같은 갈래입니다** — 런의 설정이고 해시에 들어가지 않습니다. 그래서
필드가 늘어도 구워 둔 리플레이가 그대로 유효합니다. 챌린지 문서의
「[코어 배선](../challenge.md#코어-배선)」이 그 규약이고 여기는 그것을 그대로 씁니다.

|한도|값|왜|
|--|--|--|
|본문|256KB|구워 둔 것 중 가장 긴 것이 11KB 입니다. 사람의 완주는 그 서너 배입니다|
|액션|3,000개|143수가 지금의 최장이고 사람은 그 열 배가 되지 않습니다|
|재현 시간|5초|헤드리스가 리플레이 하나를 0.1초 안에 돕니다|

`claimed` 는 **순위에 쓰지 않습니다.** 서버가 센 것과 다르면 그 사실만 기록에 남습니다 —
클라이언트의 `metrics.ts` 가 서버와 어긋난 것을 찾는 자리입니다.

## 서버의 재현

```
받음 ──▶ 큐 (Redis list)
              │  worker 가 하나씩
              ▼
        newRun(seed, deck, stake, pools, challenge)
        for action of actions: apply(action)
              │
              ├─ 예외 ──────────────────────▶ rejected: invalid_action
              ├─ phase 가 won · lost 가 아님 ──▶ rejected: unfinished
              ├─ 시간 초과 ──────────────────▶ rejected: too_long
              ▼
        metrics(steps) ──▶ 보드마다 ZADD ──▶ accepted
```

|판정|뜻|순위|
|--|--|--|
|`accepted`|재현이 끝까지 갔고 끝난 런입니다|오릅니다|
|`rejected: bad_seed`|모르는 시드 · 만료 · 이미 쓴 것 · 설정이 다른 것|—|
|`rejected: bad_fingerprint`|지문이 지금 시즌과 다릅니다. **클라이언트가 낡았습니다**|—|
|`rejected: invalid_action`|재현이 예외로 끝났습니다. **거의 나지 않습니다** — [아래](#손댄-리플레이의-처리)|—|
|`rejected: unfinished`|끝나지 않은 런입니다|—|
|`rejected: too_long`|재현이 5초를 넘었습니다|—|

### 손댄 리플레이의 처리

**코어는 규칙을 어긴 액션을 무시합니다.** 낼 수 없는 자리에서 온 `play` 는 예외가 아니라
`break` 이고, 상태가 그대로인 채 다음 액션으로 갑니다. 그래서 손댄 리플레이는 **잡히는 것이
아니라 그냥 다른 런이 됩니다.**

**그것으로 충분합니다.** 지표를 서버가 세므로, 액션에 손을 대서 얻는 것은 「내가 실제로 그렇게
두었다면 나왔을 결과」뿐입니다 — 그것은 손을 댄 것이 아니라 그렇게 논 것입니다.

`invalid_action` 은 그래서 **코어가 실제로 `throw` 한 자리에만** 남습니다. 그 판정이 나면 제출이
아니라 코어를 봅니다.

**챌린지 런의 재현도 같은 경로입니다.** `newRun` 이 `challengeId` 를 받아 시작 소지품과 규칙을 얹고, 그다음은 일반 런과 한 줄도 다르지 않습니다 — 서버가 챌린지를 아는 자리가 그 인자 하나뿐입니다.

**같은 코어이므로 `invalid_action` 이 클라이언트에서 날 수 없습니다** — 클라이언트가 받아들인
액션은 서버도 받아들입니다. 그것이 나면 리플레이가 코어를 지나지 않고 만들어진 것입니다.

**비동기인 이유는 큐 하나로 폭주를 받기 위해서입니다.** 재현이 0.1초라도 동시에 1,000개면
100초이고, 그동안 HTTP 를 잡아 두면 서버가 그 수만큼의 연결을 듭니다. 202 를 주고 클라이언트가
`GET /runs/{id}` 로 봅니다 — 대개 첫 조회에서 끝나 있습니다.

## 규칙 지문

**코어와 데이터가 조금이라도 다르면 같은 리플레이가 다른 결과를 냅니다.** 그래서 클라이언트와
서버가 같은 규칙인지를 매 제출에서 확인합니다.

```
version.json
{
  "fingerprint": "a3f9…",     // 구워 둔 리플레이 13개의 finalHash 를 이어 FNV-1a
  "builtAt": "2026-09-02T…"
}
```

|왜 리플레이의 해시입니까|
|--|
|코어의 소스 해시는 주석 하나에 바뀌고, 데이터의 해시는 조커 그림 하나에 바뀝니다. **리플레이의 해시는 규칙이 바뀔 때만 바뀝니다** — `bake-replays.ts --check` 가 이미 그것을 그렇게 씁니다|

**챌린지가 들어오는 배포가 시즌을 나눕니다.** 챌린지는 `RuleKind` 12종을 더하고 대조 누락 3건을
함께 고치므로 구워 둔 리플레이의 해시가 움직입니다 — 그 배포에 `season` 행 하나가 따라야
합니다.

빌드가 `version.json` 을 씁니다. 서버는 자기 빌드의 지문을 갖고, **시즌 표의 지문과 자기 것이
다르면 부팅하지 않습니다** — 서버가 낡은 채로 제출을 받으면 전부 `bad_fingerprint` 가 되고,
그것은 클라이언트 탓으로 보입니다.

**지문이 바뀌는 배포가 곧 시즌 교체입니다.** 배포 절차의 한 줄로 둡니다 — `season` 표에
새 행을 넣지 않으면 서버가 뜨지 않습니다.

## 클라이언트의 몫

|때|무엇|
|--|--|
|랭크 런 시작|시드 발급. 실패하면 「지금은 랭크 런을 시작할 수 없습니다」 — 그냥 시드로 시작할지 묻습니다|
|런 도중|액션을 `clover.run.actions` 에 이어 적습니다. **세이브와 같은 자리이고 이어하기가 이것을 그대로 씁니다**|
|런 끝|`POST /runs`. 실패하면 `clover.pending` 에 두고 다음 부팅에서 다시 보냅니다. 시드의 24시간 안이면 받습니다|
|판정 뒤|순위와 등급을 받아 끝난 판에 적습니다 — [화면](screens.md#런이-끝난-판)|

**액션 기록은 이미 필요한 것이었습니다.** 이어하기를 상태 저장으로 하면 상태 구조가 바뀔 때
세이브가 깨지고, 액션 저장으로 하면 다시 돌리면 됩니다. 리더보드가 그것을 강제한 것뿐입니다.

## 남는 구멍

정직하게 적어 둡니다. **막지 않는 것이고, 막지 않는 이유가 있습니다.**

|구멍|왜 두어 둡니까|
|--|--|
|사람이 아니라 봇이 놀아 올리는 것|재현으로는 가를 수 없습니다. 액션 사이의 시간을 받으면 되지만 그것은 조작이 더 쉽습니다. 신고와 수동 조치가 자리입니다|
|한 사람이 계정 여럿|제공자가 한 사람에게 계정을 여럿 주면 우리가 알 길이 없습니다|
|시드를 받아 24시간 안에 여러 번 돌려 보고 좋은 것만 올리는 것|**시드 하나에 제출 하나**이므로 같은 시드를 되돌려 다시 놀 수는 있습니다. 24시간에 20개의 한도가 그 폭을 정합니다. 좁히려면 「시작하면 그 시드는 끝난 것」으로 바꿉니다 — 그러면 브라우저를 닫은 사람이 시드를 잃습니다|
