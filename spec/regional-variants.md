# 지역 변종 — 같은 테이블의 데이터 두 벌

> [문서 목록으로](../doc/readme.md)

한 테이블이 **데이터를 여러 벌** 가지는 것에 대한 설계입니다. 스키마는 하나이고 행만 갈립니다.

지금은 그것을 **별개의 테이블로 읽고 있습니다.** `Admiral`과 `Admiral_BCCN`이 서로 다른 타입
두 개가 되어, 13개 언어 전부에 `AdmiralBccn` 클래스가 하나씩 더 생깁니다. 그 클래스는
**누구도 선언한 적이 없는 타입**입니다 — 시트가 말한 것은 「이 테이블의 중국 데이터」이지
「중국용 테이블」이 아닙니다.

[로드맵 7번](../doc/roadmap.md#다음에-할-것)이 「분리해 남겼다」고 적어 둔 항목입니다.

---

## 1. 규격

어떤 레이아웃은 정의된 이름의 접미사로 지역을 표시합니다.

```
Admiral            ← 원본
Admiral_BCCN       ← 같은 테이블의 다른 지역 데이터
```

|규칙|내용|
|--|--|
|**같은 테이블입니다**|스키마가 하나이고 행만 두 벌입니다|
|**스키마가 같아야 합니다**|다르면 오류입니다. 지금은 조용히 다른 타입 두 개가 됩니다|
|**파일은 두 개**|`Admiral.tcb`와 `Admiral_BCCN.tcb`. **접미사의 구분자를 유지합니다** — 지금은 `AdmiralBCCN.tcb`로 나가고 있어 이름에서 변종임이 사라집니다|
|**고르는 것은 읽는 쪽**|프로그램이 접미사를 지정해 그 파일을 읽습니다|

원본 익스포터도 같습니다 — 파일 이름은 정의된 이름 그대로이고, 파일 **안**의 테이블 이름은
`_BC` 이후를 잘라낸 것입니다.

```jsonc
// Admiral_BCCN.json — 파일 이름에는 접미사가, 안에는 원본 이름이
{ ":Admiral": { … }, "Admiral": { … 38행 … } }
// Admiral.json
{ ":Admiral": { … }, "Admiral": { … 41행 … } }
```

## 2. 실측

|무엇|값|
|--|--|
|전량에서 읽히는 테이블|537|
|그중 변종|**81** (전부 `_BCCN`)|
|**원본이 함께 읽히는 변종**|**81 — 전부**|
|배포된 산출물의 변종 파일|96|

**원본 없는 변종은 하나도 없습니다.** 「원본이 없으면 어떻게 하는가」는 규칙이 필요한 경우가
아니라 오류로 두면 되는 경우입니다.

### 스키마가 다른 짝 6개

그리고 이것이 이 설계가 켜지면 **오류가 되는 것들**입니다. 지금은 다른 타입 두 개라 아무도
비교하지 않습니다.

|테이블|원본에만 있는 컬럼|변종에만 있는 컬럼|
|--|--|--|
|`Admiral`|`recruitingPointDiscountBaseValue`|`recruitingPointDiscountValue`|
|`CashShopTab`|`cashShopBannerId` · `useShowBuff`|—|
|`Mate`|`autoMateTranscendencePassiveId`|—|
|`ShipCamouflage`|`statEffect`|—|
|`TradeGoods`|`unpopularTarget`|—|
|`UserTitle`|`childStatEffect` · `statEffect`|—|

`Admiral`이 특히 볼 만합니다 — **이름이 다른 같은 컬럼**으로 보입니다. 나머지 다섯은 변종이
원본을 따라가지 못한 모양입니다. 전부 [시트 오류 보고](../samples/named-range/doc/시트-오류-보고.md)로
갑니다.

## 3. 왜 지금 표현이 틀린가 — 검증이 증명합니다

별개 테이블로 읽으면 **참조가 원본을 향합니다.** 그래서 지금 전량 검증에 「없는 행을 가리키는
참조」가 잡히는데, 실측하면 그 대부분이 가짜입니다.

```
CashShop_BCCN.subProductCategory = 1402
  CashShopTab        (80행)  → 1402 없음   ← 우리가 여기를 봅니다
  CashShopTab_BCCN   (49행)  → 1402 있음   ← 시트가 뜻한 곳
```

**93건이 이 하나의 원인**입니다. 변종의 행은 변종의 세계에서 해석되어야 하고, 그것이 이
설계가 있어야 검증이 옳아지는 이유입니다.

## 4. 설계

**핵심은 코어가 접미사의 뜻을 모른다는 것입니다.** `_BC`도 `CN`도 레이아웃의 어휘입니다.
코어가 아는 것은 「이 테이블은 데이터를 여러 벌 가지고, 벌마다 파일 이름에 붙는 꼬리표가
있다」뿐입니다.

|무엇|어디|
|--|--|
|어느 이름이 어느 테이블의 변종인지, 꼬리표가 무엇인지 판정|**레이아웃 파서**|
|테이블이 데이터를 여러 벌 가진다는 개념|`Models.Table`|
|벌마다 파일을 쓰는 것|익스포터|
|참조를 같은 벌 안에서 푸는 것|검증|
|생성되는 코드|**무변경 — 타입은 테이블당 하나입니다**|

### 4.1 모델

```csharp
/// <summary>이 테이블이 가진 데이터 한 벌.</summary>
/// <remarks>
/// 원본이 꼬리표가 빈 벌이고, 나머지가 그 뒤에 옵니다. 꼬리표는 파일 이름에 그대로 붙는
/// 문자열이며 구분자를 포함합니다 - 무엇을 뜻하는 꼬리표인지는 레이아웃이 알고 코어는
/// 모릅니다.
/// </remarks>
public sealed class TableData
{
    public string FileSuffix { get; set; } = "";
    public List<List<Cell>> Rows { get; set; } = new();
}
```

`Table.Data`는 원본 벌을 가리키는 그대로 두고, `Table.Variants`가 나머지를 듭니다 —
**행을 읽는 기존 코드가 전부 원본을 보게** 해서 파급을 익스포터와 검증으로 한정합니다.

### 4.2 레이아웃

정의된 이름을 훑을 때 `_BC`가 있으면 원본 테이블을 찾아 거기에 벌을 붙입니다.

**순서를 가정할 수 없습니다.** 워크북의 이름 순서가 `Admiral_BCCN`을 먼저 줄 수 있으므로,
1차로 전부 테이블로 읽고 **2차에서 접기**로 합니다. 2차가 하는 일이 셋입니다.

|무엇|아니면|
|--|--|
|원본을 찾습니다|없으면 오류 — 실측 0건이므로 규칙을 만들지 않습니다|
|스키마를 대조합니다|다르면 오류. 어느 컬럼이 어느 쪽에만 있는지 셀 위치와 함께 보고합니다|
|행을 벌로 옮기고 변종 테이블을 모델에서 뺍니다|—|

### 4.3 익스포터

벌마다 파일 하나입니다. 이름은 `<테이블><꼬리표>.<확장자>`이고, 내용의 스키마는 같습니다.

```
Admiral.tcb          꼬리표 ""
Admiral_BCCN.tcb     꼬리표 "_BCCN"
```

**바이너리 형식은 바뀌지 않습니다.** 파일 하나가 테이블 하나인 것은 그대로이고, 늘어나는 것은
같은 스키마를 쓰는 파일의 개수입니다. 매니페스트에는 벌마다 한 줄이 들어갑니다.

### 4.4 참조

**같은 꼬리표를 먼저 보고, 없으면 원본을 봅니다.**

```
Admiral_BCCN 의 행이 Discovery 를 가리킬 때
  1. Discovery_BCCN 이 있으면 그 안에서 찾습니다
  2. 없으면 Discovery 에서 찾습니다
```

2번이 있어야 하는 이유가 실측에 있습니다 — 변종을 가진 테이블은 537개 중 81개뿐이므로,
변종의 행이 가리키는 대상은 **대개 변종이 없습니다.**

> **이것이 이 설계의 어려운 부분입니다.** 참조는 대상의 키를 그대로 싣고, 생성된 리더는
> 그 키로 대상 테이블을 찾습니다. 그러면 **어느 벌을 로드했는지가 참조 해석에 영향을 줍니다** —
> 런타임의 문제이지 형식의 문제가 아니고, 읽는 쪽이 같은 꼬리표의 벌을 함께 로드하는 한
> 성립합니다. 그 조건을 문서에 명시해야 합니다.

### 4.5 검증

벌마다 원본과 같은 검사를 돌립니다. 참조만 4.4의 규칙을 따르고, 인덱스 유니크·제약·배열
빈칸은 벌 안에서 각각 봅니다 — **벌끼리 키가 겹치는 것은 정상입니다.** 같은 테이블의 다른
지역판이므로 `Admiral` 1번과 `Admiral_BCCN` 1번은 같은 행의 두 판입니다.

## 5. 하지 않는 것

|무엇|왜|
|--|--|
|꼬리표의 뜻을 코어가 아는 것|`KR`·`GL`·`CN`은 이 프로젝트의 어휘입니다. 코어는 문자열로만 다룹니다|
|`--target-side`처럼 CLI로 벌을 고르는 것|고르는 것은 읽는 쪽입니다. 변환은 전부 냅니다|
|생성되는 코드에 벌의 목록을 넣는 것|파일 이름을 만드는 것은 로더의 일이고, 그 로더는 남의 것입니다|
|벌마다 다른 스키마|**오류입니다.** 그것을 허용하면 테이블이 하나라는 전제가 깨집니다|

## 6. 게이트

픽스처 하나에 다음을 담습니다.

|무엇|무엇을 지키는가|
|--|--|
|원본과 변종 한 쌍|파일이 둘 나오고 **꼬리표에 구분자가 남는 것**|
|생성된 코드에 타입이 하나뿐인 것|변종이 타입을 만들지 않는 것|
|변종의 행이 변종 대상을 가리키는 참조|4.4의 1번|
|변종의 행이 변종 없는 대상을 가리키는 참조|4.4의 2번|
|컬럼이 어긋난 쌍|오류가 나고 **어느 컬럼인지** 말하는 것|

그리고 **샘플에서 재는 것**: 지금 잡히는 「없는 행 참조」 111건 중 93건이 사라져야 합니다.
사라지지 않으면 4.4의 해석이 틀린 것입니다.
