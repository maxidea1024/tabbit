# mabbit — 워크북 3-way 의미 병합

> [문서 목록으로](../doc/readme.md)

---

## 1. 요약

**워크북을 파일이 아니라 표로 병합합니다.** 두 사람이 같은 `.xlsx`를 수정하였을 때, 셀의
위치가 아니라 **테이블·행 키·컬럼**의 3단계로 정합하여 병합하고, 병합할 수 없는 자리만
충돌로 보고합니다.

이것이 성립하는 근거는 하나입니다 — **이 저장소는 그 워크북의 구조를 이미 읽을 수 있습니다.**
어느 시트가 표인지, 어느 사각형이 테이블의 경계인지, 어느 컬럼이 기본 인덱스인지를 레이아웃
파서가 산출합니다. 범용 엑셀 병합 도구가 행을 위치로 정합할 수밖에 없는 자리에서, 이 도구는
**키로 정합**할 수 있습니다.

|무엇|현재|이 스펙 이후|
|--|--|--|
|같은 워크북의 동시 수정|한쪽의 작업이 소실됩니다. [여러 사람이 함께 쓸 때](multi-user-operations.md#31-엑셀--파일-단위-소유)가 도구의 상한으로 기재해 둔 자리입니다|겹치지 않는 수정은 병합되고, 겹치는 자리만 셀 단위로 보고됩니다|
|워크북 두 개의 차이 확인|수단이 없습니다. 변환한 뒤 히스토리에서만 확인합니다|`--diff`가 테이블·행·셀 단위로 산출합니다|
|병합 결과의 신뢰|—|병합 결과에 **검증 파이프라인을 그대로 적용**합니다. 중복 id와 깨진 참조가 커밋 전에 검출됩니다|

**대상은 파일로 존재하는 워크북입니다.** 구글 스프레드시트는 파일이 아니므로 대상이 아니고,
그쪽의 동시 편집은 [id 대역 분할](multi-user-operations.md#32-구글-스프레드시트--보호된-범위와-id-대역)이
계속 담당합니다.

## 2. 배치 — `tools/`의 별도 프로그램

**`tabbit` 본체에 넣지 않습니다.** `tools/mabbit/`에 자체 `.csproj`를 둔 별도 실행
파일(`mabbit`)이며, 이 저장소에는 이미 같은 형태의 선례가 둘 있습니다.

**폴더 이름은 소문자입니다.** 실행 파일 이름과 같은 표기이므로 어느 플랫폼의 셸에서도 대문자를
기억할 필요가 없고, `src/`·`bench/`·`doc/`의 표기와도 일치합니다.

이름은 `merge` + `tabbit`입니다. 계열이 유지되므로 **완성된 브랜드 자산에서 아이콘과 로고를
파생만 하면 됩니다.**

|선례|무엇|
|--|--|
|`bench/Tabbit.Bench.csproj`|자체 설정을 가진 형제 실행 파일. `TreatWarningsAsErrors`도 nullable도 켜지 않습니다|
|`test/fixtures/tools/FixtureGen/`|**NPOI로 `.xlsx`를 작성하는 도구.** 본체가 그 의존을 지지 않도록 `src/` 밖에 둔 것입니다|

### 2.1 적용되지 않는 규칙

[CLAUDE.md](../CLAUDE.md)의 코어 규칙은 `src/` 아래를 범위로 합니다. 다음은 이 프로그램에
적용되지 않습니다.

|규칙|적용되지 않는 근거|
|--|--|
|의존 추가의 억제|`tabbit`의 자립 단일 파일 배포에 포함되지 않으므로 배포본 크기와 무관합니다. 쓰기 라이브러리·GUI 프레임워크를 자유롭게 선택할 수 있습니다|
|`TreatWarningsAsErrors`·nullable|형제 프로젝트 2개가 이미 켜지 않았습니다. **다만 새로 작성하는 코드이므로 켜는 편을 권장합니다** — 나중에 켜는 비용이 662개였던 전례가 있습니다|
|코어에 프로젝트 이름 금지|`src/` 밖입니다. 실질적으로는 그럴 이유도 없습니다 — 병합기는 레이아웃에게 사각형과 키 컬럼을 확인할 뿐입니다|
|골든 무변경|산출물 생성 경로가 아니므로 골든에 영향을 주지 않습니다|

### 2.2 여전히 지키는 것

- **`Tabbit.slnx`에 `/tools/` 폴더로 등재**합니다. 솔루션 밖의 프로젝트는 빌드되지 않는
  프로젝트가 됩니다.
- **크로스플랫폼**을 유지합니다. 병합 드라이버는 CI에서 리눅스로 실행되어야 합니다.
- **엑셀 설치를 요구하지 않습니다.** 참고 구현이 그것을 요구하여 CI에서 사용할 수 없게 된
  자리입니다.

## 3. 참고한 구현 — XlsxMerge

넥슨코리아가 공개한 [XlsxMerge](https://github.com/kyungjae-nexon/xlsxmerge)(MIT)를 참고
대상으로 확인하였습니다. 엑셀 문서를 행 단위로 비교하고 3-way 병합하는 도구이며, SCM 연동
가이드를 함께 제공합니다.

### 3.1 가져오는 것

|무엇|근거|
|--|--|
|**행 단위를 병합의 단위로 삼는 판단**|표 형태의 문서에서 변경은 대부분 행 방향으로 발생합니다. 셀 단위 정합만으로는 행 삽입 하나가 그 아래 전부를 변경으로 보고합니다|
|**값과 수식으로 범위를 한정하는 판단**|차트·도형·매크로·주석을 병합 대상에서 제외하고 그 사실을 먼저 밝힙니다. 경계를 명시한 것이 그 도구가 신뢰를 얻는 방식입니다|
|**SCM 연동을 별도 문서로 제공하는 구성**|병합 도구는 SCM에 등록되지 않으면 사용되지 않습니다. 등록 절차가 기능의 일부입니다|
|**병합 결과를 커밋 전에 확인하도록 안내하는 것**|자동 병합을 무조건 신뢰하게 만들지 않습니다|

### 3.2 가져오지 않는 것

|무엇|근거|
|--|--|
|`diff.exe`·`diff3.exe` **외부 프로세스 의존**|행을 텍스트 줄로 직렬화해 범용 diff3에 넘기는 방식입니다. 정합이 **위치 기반**이 되므로 행 순서가 변경된 워크북에서 정확도가 낮아지고, 실행 파일 2개를 배포본에 동봉해야 합니다. 키로 정합하면 그 단계가 필요하지 않습니다|
|**엑셀 설치와 Windows 요구**|§2.2|

## 4. 설계

### 4.1 병합이 요구하는 범위 — 레이아웃까지

**필요한 것은 레이아웃까지이고 쿠킹 전체가 아닙니다. 이 판단이 나머지 설계를 결정합니다.**

워크북을 `Model`까지 쿠킹하여 `ModelFingerprint`·`SnapshotDiff`를 재사용하는 구성은 성립하지
않습니다 — **enum 선언과 참조는 워크북을 가로질러 해석**되므로, 병합 대상 파일 하나만 쿠킹하면
다른 워크북에 선언된 enum에서 실패합니다. 전체 소스를 쿠킹하면 성립하나, 병합 1회마다 워크북
전부를 읽는 비용이 됩니다.

병합에 필요한 것은 셋뿐입니다.

|필요한 것|어디서|
|--|--|
|표 사각형|`src/Cooking/Layouts/` — 레이아웃 파서가 격자 위에서 산출합니다|
|키 컬럼과 컬럼 이름|같은 자리|
|셀의 값|`src/Importers/` — 격자 그대로입니다|

**값 비교에 정규화가 필요하지 않습니다.** `CanonicalValue`가 존재하는 이유는 서로 다른 시점의
두 모델을 대조하기 위해서인데, 병합은 `base`·`mine`·`theirs`를 **같은 코드가 같은 실행에서**
읽으므로 원시 셀 텍스트의 비교로 충분합니다. 결과로 타입 해석·enum 해석·참조 해석이 병합
경로에서 전부 제거됩니다.

|자리|재사용|
|--|--|
|`src/Importers/XlsxImporter.cs` · `Xlsx/SheetGridReader.cs`|**그대로 사용합니다.** 스트리밍 격자 읽기|
|`src/Cooking/Layouts/`|**그대로 사용합니다.** 표 경계와 키 컬럼|
|`src/Models/Raw/` · `Location.cs`|**그대로 사용합니다.** 보고가 가리킬 자리이자 쓰기가 찾아갈 자리|
|`src/History/SnapshotDiff.cs` · `ModelFingerprint.cs`|**사용하지 않습니다.** `Model` 위에서 동작하는 것이고 병합은 격자 위에서 동작합니다. 판정은 새로 작성하며 §4.3·§4.4의 표가 그 전부입니다|

> **앞선 판단을 정정한 자리입니다.** 이 스펙의 초안은 「1·2단계는 기존 비교 경로에 상대를
> 하나 더 붙이는 작업」이라고 기재하였으나, 단일 파일 쿠킹이 성립하지 않으므로 그렇지
> 않습니다. 판정 로직을 새로 작성하는 대신 쿠킹 이후의 해석 단계 전부가 제거되므로, 순
> 비용은 증가하지 않습니다.

### 4.2 스키마의 출처 — 주입 가능한 자리

병합 엔진은 인터페이스 하나만 참조합니다.

```csharp
interface ITableSchema
{
    IReadOnlyList<TableRegion> TablesIn(string workbookPath);
}

record TableRegion(
    string Name, string Sheet,
    int FirstRow, int FirstColumn, int LastRow, int LastColumn,
    int KeyColumn, IReadOnlyList<string> ColumnNames);
```

|구현|무엇|
|--|--|
|`RecipeSchema`|`--recipe`가 주어졌을 때. `--path`로 소스 항목을 판정하고 그 항목의 레이아웃으로 사각형을 산출합니다. **정확합니다**|
|`HeuristicSchema`|`--recipe`가 없을 때. 시트 하나를 표 하나로, 첫 행을 헤더로, 첫 컬럼을 키로 간주합니다. `--key <시트>:<컬럼>`으로 덮어씁니다|

recipe 없이도 동작하므로 이 도구는 이 저장소 밖의 워크북에도 적용되고, 나중에 분리하여
공개하는 선택지가 열린 채로 남습니다.

### 4.3 셀의 3-way 판정

`base`를 O, `mine`을 A, `theirs`를 B로 둡니다.

|조건|결과|
|--|--|
|A = B|그 값|
|A = O, B ≠ O|B를 채택|
|B = O, A ≠ O|A를 유지|
|A ≠ O, B ≠ O, A ≠ B|**충돌**|

### 4.4 행과 컬럼의 판정

정합 기준은 **테이블 이름 → 기본 인덱스의 셀 텍스트 → 컬럼 이름**입니다. 행 순서는 `mine`
쪽을 유지하고, `theirs`에만 있는 행은 그 테이블 사각형의 마지막 행 다음에 추가합니다 —
순서가 산출물의 바이트에 영향을 주므로 임의로 정렬하지 않습니다.

|상황|결과|
|--|--|
|한쪽만 행을 추가|추가합니다|
|양쪽이 **같은 키**의 행을 추가하고 내용이 다름|**충돌.** [구글 시트 쪽에서 이미 확인된 사고](multi-user-operations.md#32-구글-스프레드시트--보호된-범위와-id-대역)와 같은 것이며, 파일 워크북에서는 이 자리에서 검출됩니다|
|한쪽이 삭제, 다른 쪽이 수정|**충돌**|
|양쪽이 삭제|삭제합니다|
|한쪽만 컬럼을 추가|추가하고 상대 쪽 행의 그 칸은 빈 칸입니다|
|양쪽이 같은 이름의 컬럼을 추가|헤더 셀이 다르면 **충돌**|
|한쪽이 컬럼 이름을 변경, 다른 쪽이 그 컬럼의 셀을 수정|**충돌.** 이름 변경은 삭제와 추가로 나타나므로 값 변경과 겹친 자리에서는 대응을 확정할 수 없습니다|

### 4.5 표 밖의 영역

레이아웃이 덮지 않는 시트와 셀은 의미 병합의 대상이 아닙니다. 그러나 **변경이 있었다는 사실은
검출합니다** — 표 사각형 밖의 셀들을 시트마다 해시하여 3개 파일을 대조하고, 양쪽이 서로 다르게
변경하였으면 충돌로 보고합니다.

이 장치가 없으면 「병합에 성공하였으나 남의 수정이 사라진 파일」이 산출됩니다.
**감지되지 않는 소실은 충돌보다 나쁩니다.**

### 4.6 결과 워크북의 작성

**`mine` 파일을 운반체로 삼습니다.** 새 워크북을 생성하지 않고 `mine`의 패키지를 복사한 뒤
필요한 파트만 다시 씁니다. 서식·차트·조건부 서식·매크로·병합된 셀은 손대지 않은 바이트로
남습니다.

**의존을 자유롭게 선택할 수 있게 되었으나, 이 자리에서는 그것이 자동으로 이득이 아닙니다.**

|후보|이득|손실|
|--|--|--|
|**직접 스트리밍 패치** (`System.IO.Compression` + `XmlReader`/`XmlWriter`)|표 사각형 밖이 **바이트 단위로 동일**합니다. 그것이 그대로 게이트가 됩니다. 메모리 특성이 현재 리더와 같습니다|행 삽입의 부수 갱신(정의된 이름·병합 셀·수식 참조)을 직접 구현해야 합니다|
|**NPOI** (저장소에 이미 있습니다)|기존 워크북을 열어 수정할 수 있고, 행 삽입의 부수 갱신을 라이브러리가 담당합니다|**워크북 전체가 재작성되므로 「표 밖 바이트 동일」 게이트가 성립하지 않습니다.** 손대지 않은 시트의 XML도 변경되고, 라이브러리가 보존하지 못하는 파트는 감지 없이 사라집니다. 61 MiB 워크북에서 DOM이 **3.4 GB**로 [실측](streaming-workbook-reader.md)된 자리이기도 합니다|
|**OpenXML SDK**|MS 공식이고 SAX 경로가 있습니다|SAX 경로에서는 `sharedStrings`·`styles` 인덱스를 직접 다루게 되므로 직접 패치와 작업량이 비슷해집니다|

**3단계는 직접 패치로 진행합니다.** 라이브러리가 실제로 크게 줄이는 것은 4단계의 부수
갱신이므로, 도입 여부는 §5.1의 실측 이후에 판단합니다. 판단 기준은 「표 밖 바이트 동일
게이트를 유지할 수 있는가」입니다.

세부 처리는 다음과 같습니다.

|사항|처리|근거|
|--|--|--|
|수정 범위|표 사각형 안의 셀만 씁니다. 그 밖은 토큰 단위로 통과시킵니다|검사 가능한 불변식입니다|
|문자열 값|`t="inlineStr"`로 적습니다|`sharedStrings.xml`을 재작성하지 않습니다. 항목을 추가하면 인덱스 체계 전체가 수정 대상이 됩니다|
|수식 셀|`<f>`가 있는 셀이 병합 대상이면 **충돌로 보고**합니다|수식의 결과만 변경하면 다음 재계산에서 되돌아갑니다. 수식 자체의 병합은 §8의 미결입니다|
|캐시된 수식 결과|`xl/calcChain.xml`을 삭제하고 `<calcPr fullCalcOnLoad="1"/>`을 설정합니다|셀 값이 변경되면 다른 수식의 캐시된 결과가 낡습니다|

### 4.7 결과의 검증

병합 결과 파일에 **`tabbit --validate-only`를 이어서 실행**합니다. 중복 id, 범위 위반, 깨진
참조가 커밋 전에 검출되고, 보고에는 셀 위치가 포함됩니다.

범용 엑셀 병합 도구가 육안 확인에 의존하는 자리이며, 이 저장소는 **읽는 쪽을 이미 갖고
있습니다.** 별도 프로세스 호출이므로 병합기가 쿠킹 전체를 끌어안지 않아도 성립합니다.

## 5. 단계

앞의 것이 없으면 뒤의 것을 확인할 수 없는 순서입니다.

|단계|무엇|쓰기|크기|게이트|
|--|--|--|--|--|
|1|**`--diff` — 워크북 2개의 표 단위 차이.** 격자 읽기 + 레이아웃 + 키 정합|없음|작음|보고서 골든. 픽스처 워크북 쌍에서 테이블·행·셀 차이가 기대와 일치|
|2|**3-way 판정과 충돌 보고.** `--merge`가 판정만 산출하고 파일을 쓰지 않습니다|없음|중간|§4.3·§4.4 판정표의 **전 항목 픽스처**. 표 밖 지문(§4.5) 포함|
|3|**셀 값 쓰기.** 직접 스트리밍 패치|셀 값만|중간|**왕복 게이트** — ① 표 안은 기대값 ② 표 사각형 밖은 원본과 바이트 동일 ③ 엑셀이 복구 대화상자 없이 여는 것|
|4|**행 추가·삭제**|행|**큼**|정의된 이름 범위의 확장, 아래 영역 비침범 확인|
|5|**SCM 연동.** git 병합 드라이버 등록 + §4.7 검증 연결|—|중간|실제 저장소에서 `git merge`를 수행하는 통합 테스트. 겹치는 수정이 충돌로, 겹치지 않는 수정이 병합으로 종료|
|6|**비교·충돌 편집 GUI**|—|—|§6|

### 5.1 4단계가 큰 이유

행 추가는 그 아래 행들의 위치를 이동시킵니다. 이동에 함께 따라와야 하는 것이 셋입니다 —
정의된 이름의 참조 범위, 병합된 셀의 범위, 그 영역을 가리키는 수식과 조건부 서식.

그래서 **4단계는 아래가 비어 있을 때만 추가하는 것에서 시작합니다.** 표 사각형 아래에 다른
내용이 있으면 충돌로 보고합니다. 레이아웃 문서가 이미
[엔티티 사이를 한 칸 이상 띄우도록](../doc/sheets.md) 규정하고 있으므로 이 제한에 걸리는 배치는
많지 않을 것으로 보이나, **미측정**입니다 — 3단계를 마친 뒤 샘플 워크북에서 실측하여 시프트
구현이 필요한지, 필요하다면 §4.6의 라이브러리 도입이 그 대안인지 결정합니다.

## 6. GUI — 6단계에 두는 근거

**보류가 아니라 순서입니다.** `tools/`의 별도 프로그램이므로 UI 프레임워크 도입에 제약이
없고, 크로스플랫폼 요건(§2.2)을 충족하는 선택지가 있습니다.

뒤에 두는 이유는 하나입니다 — **모양을 결정할 자료가 2단계에서 산출됩니다.** 충돌의 빈도와
종류를 확인하기 전에 작성하면 짐작한 충돌을 대상으로 설계하는 것이 됩니다. v104에서 인코딩보다
계측(`EncodingReport`)을 먼저 작성한 뒤 계획이 변경된 것과 같은 자리입니다.

그 사이에도 사용은 가능합니다. 충돌 보고가 셀 위치를 포함하므로 엑셀에서 해당 셀로 이동할 수
있습니다.

## 7. 하지 않는 것

명시하지 않으면 결손으로 오해되는 것들입니다.

|무엇|근거|
|--|--|
|서식·차트·도형·매크로·피벗·조건부 서식의 병합|`mine`의 것이 그대로 남습니다. 값이 아닌 것을 병합하려면 워크북 전체의 모델이 필요하며, 이 저장소가 워크북에서 읽는 것은 값입니다|
|셀 주석의 병합|`mine`의 것이 남습니다. `WorkbookPackage`가 읽고는 있으나 컬럼 설명으로만 사용하며, §4.5의 표 밖 판정에도 걸리지 않으므로 **문서에 명시합니다**|
|수식 자체의 3-way 병합|수식 셀은 충돌로 보고합니다. 참조 범위의 이동을 함께 판정해야 하므로 별개의 크기입니다|
|구글 스프레드시트|파일이 없으므로 병합할 대상이 없습니다|

## 8. 미결

- **병합 드라이버의 시작 비용.** git은 충돌한 파일마다 드라이버를 1회 실행합니다. `tools/`
  프로젝트가 `src/Tabbit.csproj`를 참조하면 구글 API·DB 드라이버·Roslyn이 함께 로드됩니다.
  **미측정**이며, 문제가 확인되면 격자 읽기와 레이아웃만 별도 어셈블리로 분리합니다.
- **행 시프트의 필요 여부.** §5.1의 실측이 선행되어야 4단계의 크기와 §4.6의 라이브러리 도입
  여부가 확정됩니다. **미측정**입니다.
- **`.xlsb`의 쓰기.** 읽기는 지원하나 쓰기는 형식이 다릅니다(바이너리 레코드 스트림). 1·2단계는
  형식과 무관하게 동작하고, 3단계 이후를 `.xlsx`로 한정할지 결정이 필요합니다.
- **확장자 없는 임시 파일.** git이 넘기는 `%O`·`%B`는 `.merge_file_XXXXXX` 형태이며 확장자가
  없습니다. `--path`가 주는 저장소 상대 경로의 확장자를 사용하고, 그것으로도 판정되지 않으면
  파일 시그니처(`PK` + `[Content_Types].xml`)로 판정합니다. **1단계에서 함께 처리합니다** —
  나중에 발견하면 5단계 전체가 동작하지 않는 원인이 됩니다.
- **CI에서의 자동 병합 허용 여부.** 사람이 확인하지 않은 병합 결과를 CI가 커밋하도록 할지는
  운영 규약의 결정이며, [여러 사람이 함께 쓸 때](multi-user-operations.md)의 「하나의 산출물
  트리에 쓰는 주체는 하나」 원칙과 함께 판단합니다.
- **로드맵상의 순서.** [남은 항목](../doc/roadmap.md#아직-안-함)은 깊은 스큐의 나머지 12개 언어와
  범용 압축 레이어입니다. 이 기능을 그 앞에 둘지 뒤에 둘지는 정해지지 않았습니다.

## 9. CLI와 SCM 연동

### 9.1 옵션

```
mabbit --diff  --base <파일> --mine <파일> [--recipe <파일>] [--path <경로>]
mabbit --merge --base <파일> --mine <파일> --theirs <파일> --result <파일> \
       [--recipe <파일>] [--path <경로>] [--key <시트>:<컬럼>]
```

`--recipe`가 없으면 §4.2의 `HeuristicSchema`로 동작합니다. `--path`는 어느 소스 항목이 그
파일을 덮는지 판정하는 데 사용하며, §8의 확장자 판정에도 함께 쓰입니다.

### 9.2 git 등록

```gitattributes
*.xlsx merge=mabbit
*.xlsb merge=mabbit
```

```gitconfig
[merge "mabbit"]
    name = Mabbit workbook merge
    driver = mabbit --merge --base %O --mine %A --theirs %B --result %A --path %P --recipe recipe.jsonc
```

git은 결과를 `%A`에 쓰고 종료 코드로 판정합니다 — 0이 성공, 그 밖이 충돌입니다.

### 9.3 그 밖의 SCM

Perforce·PlasticSCM·TortoiseGit은 인자 순서만 다르고 요구하는 것은 같습니다(base·mine·theirs·result
4개 경로와 종료 코드). 연동 문서는 `doc/`에 별도로 두고, 이 스펙은 git까지만 규정합니다.
