# Luban 기능 대조

> **문서 세트 밖의 정리 노트입니다.** `doc/` · `spec/`이 아니라 `notes/`에 있는 이유가
> 그것이고, 사이트에도 올라가지 않습니다. 문서 목록은 [doc/readme.md](../doc/readme.md)입니다.

같은 문제를 푸는 외부 도구 **Luban**과 tabbit의 기능 대조입니다. **이미 있는 것까지 전부
표에 넣었습니다** — 없는 것만 나열하면 도입 판단의 분모가 보이지 않고, 「대체 수단이 이미
있는 것」과 「수단이 없는 것」이 같은 무게로 읽히기 때문입니다.

---

## 1. 요약

|무엇|결과|
|--|--|
|**결함**|**1건** — `datetime`의 타임존 미정의(§3). 유일하게 즉시 조치 대상입니다|
|**대체 수단 없이 없는 것**|11건. 그중 도입을 권고하는 것은 4건입니다(§5)|
|**다른 방식으로 있는 것**|9건. 형태가 달라도 목적은 달성됩니다|
|**의도적 부재**|4건. 판단이 이미 기록되어 있습니다(§6)|
|**tabbit에만 있는 것**|16건. 게이트·형식·추적 계열입니다|

**전체 판정은 이렇게 갈립니다 — 게이트 설계와 산출 형식은 tabbit이 앞서 있고, 데이터
표현력과 입력 다양성은 Luban이 앞서 있습니다.** §5의 우선순위는 이 판정을 따릅니다.
가치가 같다면 표현력 쪽을 먼저 두었습니다.

## 2. 조사 범위와 방법

|항목|내용|
|--|--|
|대상|Luban 4.11.0 · 커밋 `8f7f4e1` (2026-08-15) · MIT|
|읽은 코드|`Luban.Core` · `Luban.DataLoader.Builtin` · `Luban.DataTarget.Builtin` · `Luban.DataValidator.Builtin` · `Luban.Schema.Builtin` · `Luban.L10N` · CLI|
|읽은 문서|공식 문서의 기능 목록·스키마·엑셀·품질·레퍼런스 절|
|tabbit 쪽 근거|이 저장소의 코드와 `spec/` · `doc/`|

**판정 어휘는 5가지입니다.**

|판정|뜻|
|--|--|
|**있음**|같은 목적의 수단이 있습니다|
|**다른 방식**|형태는 다르나 목적은 달성됩니다|
|**없음**|수단이 없습니다|
|**의도적 부재**|하지 않기로 한 판단이 기록되어 있습니다|
|**tabbit만**|Luban에 대응이 없습니다|

**이 대조의 한계 하나** — Luban을 실행해서 산출물을 대조한 것이 아니라 **코드와 문서를
판독한 결과입니다.** 실측은 §3의 1건뿐이고, 그 1건은 tabbit 쪽 측정입니다. Luban의 동작에
대한 서술은 전부 판독이므로, 도입을 결정한 항목은 그 시점에 해당 기능만 실행해 확인하는
편이 안전합니다.

## 3. 즉시 조치 — `datetime`의 타임존 미정의

**등급: 높음 · 근거: 실측**

[`CookingContext.cs`](../src/Cooking/CookingContext.cs)의 값 파싱이
`DateTime.Parse(rawValue, InvariantCulture)`이고 `DateTimeStyles`를 지정하지 않습니다.
이 API는 오프셋 표기가 붙은 문자열을 **변환하는 머신의 로컬 시각으로 변환합니다.**
KST 머신에서 측정한 값입니다.

|셀 값|산출 ticks|`Kind`|해석|
|--|--|--|--|
|`2026-01-01 09:00:00`|639028548000000000|`Unspecified`|표기 그대로|
|`2026-01-01T09:00:00Z`|639028872000000000|`Local`|**18:00으로 변환됨**|
|`2026-01-01T09:00:00+09:00`|639028548000000000|`Local`|09:00|

두 번째 줄이 문제입니다. **같은 시트를 UTC 러너에서 변환하면 09:00의 ticks가 산출되므로,
변환한 머신에 따라 산출 바이트가 달라집니다.** 파일에는 ticks만 실리고 어느 기준의 시각인지가
남지 않으므로, 소비 측에서 이 차이를 검출할 방법도 없습니다.

**게이트가 닿지 않는 자리입니다.** `FixtureGen`의 `datetime` 값은 전부 오프셋 없는
`yyyy-MM-dd HH:mm:ss` 표기여서 골든과 적합성 코퍼스가 이 경로를 통과하지 않습니다.
CI가 UTC 러너에서 도는데도 통과하는 이유가 이것입니다.

### 3.1 조치

|무엇|내용|
|--|--|
|**기준 시간대의 선언**|recipe에 `TimeZone` 항목을 두고 오프셋이 붙은 값을 그 기준으로 정규화합니다. Luban의 `--timeZone`이 같은 자리입니다|
|**오프셋이 없는 값의 해석**|결정이 필요합니다 — 선언된 시간대의 시각으로 볼지, 표기 그대로 둘지. 기존 산출물과의 정합이 판단 근거입니다|
|**게이트 보강**|픽스처에 `Z` 표기와 오프셋 표기 값을 추가합니다. **이것이 없으면 같은 결함이 다시 들어옵니다**|

**부담은 작습니다.** 파싱 1곳과 recipe 항목 1개이고, 산출 형식과 생성 코드는 바뀌지 않습니다.
다만 기존 시트에 오프셋 표기 값이 있다면 **골든과 배포된 데이터가 함께 움직입니다** — 값이
달라지는 변경이므로 그 diff는 리뷰 대상입니다.

## 4. 전체 대조표

### 4.1 입력

|Luban|tabbit|판정|
|--|--|--|
|csv · xls · xlsx · xlsm|xls · xlsx · xlsm · **xlsb**|**있음** — csv는 없고 `.xlsb`는 tabbit만|
|json · xml · yaml · lua 데이터 파일|없음|**없음** → §5.6|
|디렉터리 재귀 · 파일 1개가 레코드 1개|없음|**없음** → §5.6|
|—|구글 스프레드시트(OAuth·서비스 계정, 셀 링크 보고)|**tabbit만**|
|시트 지정 · 무시 접두어|`IncludeSheets` · `ExcludeSheets` · `#` 접두어|**있음**|
|테이블 1개 = 입력 파일 여러 개|없음|**없음** — 값이 낮습니다(아래 주석)|
|XML 스키마 정의 파일|시트가 스키마|**의도적 부재**|
|—|스트리밍 워크북 읽기(peak 7.4 GB → 2,757 MB)|**tabbit만**|
|—|레이아웃 파서 층 — 다른 규칙으로 쓰인 시트 읽기|**tabbit만**|

> 「테이블 1개 = 입력 파일 여러 개」의 값을 낮게 둔 근거는 tabbit이 워크북 여러 개를 한 번에
> 읽고 [행 벌](../spec/layout/table-row-sets.md)이 데이터 여러 벌을 담당한다는 점입니다. 다만 **같은 이름의
> 테이블이 두 곳에서 선언될 때의 처리는 확인하지 않았습니다** — `Model.Tables.Add`에 중복
> 검사가 보이지 않으므로 별도 확인이 필요한 자리입니다.

### 5.1 행 단위 태그

Luban은 레코드마다 태그를 부여하고 `--includeTag` · `--excludeTag`로 산출에서 제외합니다.

**가치** — 테스트 행 · 작업 중인 행 · 특정 빌드용 행을 **시트를 분리하지 않고** 릴리스에서
제외할 수 있습니다. tabbit의 제외 수단은 시트 · 테이블 · 컬럼 단위이므로(`TargetSide` ·
`IncludeSheets` · 필드명의 `#`) 행 단위는 시트를 나누는 것이 유일한 방법입니다. 시트를 나누면
스키마가 두 벌이 되고, 그것이 [행 벌](../spec/layout/table-row-sets.md)이 이미 기재한 문제입니다.

**부담** — 산출 형식과 생성 코드는 바뀌지 않습니다. 결정이 필요한 것은 3가지입니다.

|결정할 것|내용|
|--|--|
|**태그를 적는 자리**|레이아웃마다 다릅니다. `tabbit` 레이아웃은 컬럼 1개로 되나, 다른 레이아웃에는 그 자리가 없을 수 있습니다|
|**필터의 위치**|검증 앞이면 제외된 행을 가리키는 참조가 깨진 참조로 보고됩니다. 뒤이면 제외된 행의 오류까지 보고합니다. **어느 쪽이든 근거를 기재해야 하는 자리입니다**|
|**히스토리와의 관계**|제외를 삭제로 기록하면 리포트가 오염됩니다. 스냅샷을 필터 이전 데이터로 뜨는 것이 맞다고 보이나 확인이 필요합니다|

### 5.2 다형 레코드

Luban은 추상 타입과 하위 타입을 지원하고, 시트에서는 `$type` 서브 컬럼이 행마다 어느 하위
타입인지 지정합니다. 헤더는 모든 하위 타입 컬럼의 합집합입니다.

**가치** — 스킬 효과 · 조건 · 보상처럼 **행마다 형태가 다른 데이터**가 게임 데이터에서 큰
비중을 차지하고, tabbit에는 이 표현이 없습니다. 중첩 레코드는 되지만 형태가 고정입니다.
현재 방법은 컬럼을 여러 벌 펼치거나 문자열에 넣어 소비 측에서 파싱하는 것이고, 후자는
**이 도구가 제거하려는 것 자체입니다** — 검증도 타입도 닿지 않습니다.

**부담 — 이 목록에서 가장 큽니다.** 파급 범위는 다음과 같습니다.

|어디|무엇|
|--|--|
|모델|`ValueType`에 하위 타입 개념. 지금은 필드 1개가 타입 1개입니다|
|와이어|타입 태그 추가 — **형식 개정 1회**. 컬럼 지향 인코딩에서 행마다 컬럼 집합이 달라지는 것을 어떻게 담을지가 핵심이고, 이것이 가장 어려운 자리입니다|
|코드 생성|**모든 언어**에 파생 타입 선언과 판별 읽기. 상속이 없는 언어(C · Go · Rust)마다 다른 형태가 필요합니다|
|검증|하위 타입별 제약. 컬럼 제약이 「컬럼 1개 = 규칙 1벌」 전제 위에 있습니다|
|DB 익스포터|하위 타입마다 컬럼 집합이 다르므로 테이블 매핑을 새로 정해야 합니다|
|게이트|적합성 코퍼스 확장 · 골든 재기록 · 샘플 재생성|

> **그 스펙이 [다형과 참조 배열](../spec/types/polymorphism.md)이고, 와이어는 성립합니다** — 판별자
> 컬럼 하나와 변종 멤버 컬럼의 합집합이며, v103·v106의 presence가 「행마다 컬럼 집합이 다른
> 것」을 이미 담습니다. 위 표의 「형식 개정 1회」 산정이 그 문서 §6에서 없어집니다.

**권고는 스펙 선행입니다.** 와이어 설계가 성립하는지를 먼저 확인해야 하고, 성립하지 않으면
나머지 부담은 산정할 필요가 없습니다.

### 5.3 대상 구분의 일반화

[`TargetSide`](../src/Models/TargetSide.cs)는 `ClientOnly` · `ServerOnly` · `Both` 3값 플래그로
고정되어 있습니다. Luban은 이름 있는 그룹을 설정 파일에서 정의합니다.

**가치** — 에디터 빌드 · QA 빌드 · 툴 전용 테이블처럼 **세 번째 대상**이 생기면 현재 구조에는
표현할 자리가 없습니다. 「기능은 일반적으로 만들고 이름은 플러그인 쪽에 둔다」는 저장소
원칙과도 정합하는 방향의 일반화입니다.

**부담** — 대상별로 컬럼을 제외하는 것 자체는 이미 수행하고 있습니다. 비용은 이관
범위입니다 — `c` · `s` 표기가 시트의 대상 행 · recipe · CLI(`--target-side`) · 문서 · 골든에
분포하고, 기존 표기를 새 어휘의 별칭으로 남길지가 결정 사항입니다. **먼저 실측할 것은 그
표기가 등장하는 자리의 수입니다.**

### 5.4 단일 행 테이블

Luban의 `ONE` 모드는 행이 1개인 테이블을 조회 없이 필드에 직접 접근하는 객체로 산출합니다.

**가치** — 전역 설정값을 **데이터 패치만으로** 변경할 수 있습니다. 지금 같은 데이터를 두는
방법은 2가지이고 둘 다 어긋납니다.

|방법|어긋나는 점|
|--|--|
|상수셋|[코드 배포가 필요합니다](../doc/concepts.md) — 값을 수정해도 재배포 전에는 아무것도 달라지지 않습니다|
|행이 1개인 테이블|인덱스 컬럼과 조회 API를 경유합니다. 전역 설정에 인덱스 `1`을 기재하는 것은 의미 없는 컬럼입니다|

**부담** — 와이어는 그대로입니다(행이 1개인 테이블). 추가되는 것은 **모든 코드 생성 타깃의
접근자 표면 1종**과, 「행이 정확히 1개」를 확인하는 검증 규칙 1개입니다. 골든에는 픽스처
1개가 추가됩니다.

### 5.5 키 없는 목록 테이블과 복합 키

tabbit은 기본 인덱스가 필수이고 인덱스는 컬럼 1개입니다. Luban은 `LIST` 모드와 복합 인덱스를
지원합니다.

**가치** — `(stage, slot)` 조합이 키인 데이터에 인조 키 컬럼을 추가하지 않아도 됩니다.
우회가 가능하므로 가치는 중간입니다.

**부담** — 인덱스 모델이 「필드 1개」 전제 위에 있고, 조회 생성 코드가 그 전제를 사용합니다.
복합 키는 조회 시그니처가 다인자가 되므로 **모든 코드 생성 타깃이 변경됩니다.** 그리고 참조가
복합 키 테이블을 가리키는 경우는 [참조가 키 1개를 담는 현재 구조](../spec/references/reference-key-types.md)와
충돌하므로, **그 조합을 거부하는 것으로 시작하는 편이 안전합니다.**

### 5.6 비엑셀 소스

Luban은 한 테이블의 데이터를 json · xml · yaml · lua · 디렉터리에서 읽고 엑셀과 혼합합니다.

**가치** — 에디터나 툴이 산출한 구조화 데이터를 **시트로 옮기지 않고** 합류시킬 수 있습니다.
스킬 · AI 트리처럼 사람이 표에 기재하지 않는 데이터가 대상입니다.

**부담** — 확장 지점은 이미 있습니다(`ISource`와 `[TabbitSource]` 스캔). 실제 비용은 그
옆입니다.

|어디|무엇|
|--|--|
|스키마의 출처|시트에서 정의하고 데이터만 파일에서 읽는 형태가 이 저장소의 구조에 맞습니다. 파일이 스키마까지 정하면 시트가 유일한 정의 자리라는 전제가 무너집니다|
|위치 보고|`Location`이 셀 주소입니다. 파일 경로와 문서 내 위치를 담도록 확장해야 하고, **이것이 이 항목의 실제 비용입니다** — 셀 위치 보고는 이 도구의 주요 성질이므로 형태만 다르게 유지해야 합니다|
|히스토리|셀 주소 대신 경로를 기록해야 합니다|

### 5.7 참조 자원 목록 산출

Luban의 `res` 타깃은 자원 경로로 표시된 값을 모아 목록으로 산출합니다.

**가치** — 번들 패킹과 프리로드의 입력이 됩니다. tabbit은 `asset` 역할과 `Assets` 루트로
**그 목록을 이미 산출해 존재를 확인하고 있습니다** — 확인한 것을 내보내지 않고 폐기하는
상태입니다.

**부담 — 이 목록에서 가장 작습니다.** `ITarget` 구현 1개와 매니페스트 형식 결정이고, 다른
곳에 파급이 없습니다. 산출물이 추가되므로 골든에는 그 타깃을 켠 픽스처가 1개 필요합니다.

### 5.8 시트에 기재하는 제약의 확대

정규식 · 배열 길이 · 배열 내 유일성 · 기본값 금지 4가지가 없습니다(§4.5).

**가치** — 지금도 C# 규칙으로 작성할 수 있으나 **그것은 프로그래머의 작업입니다.** 시트
작성자가 컬럼 옆에 기재하는 것과 규칙 파일을 작성하는 것은 같은 검사라도 도달 범위가
다릅니다.

**부담** — `ColumnConstraints`에 항목 추가와 검증 1곳입니다. 산출 형식과 생성 코드는 변경되지
않습니다. 정규식은 「어느 방언인가」를 문서에 명시해야 하고, 배열 길이는
[배열의 옵셔널](../spec/types/array-optionality.md)이 정한 규칙과의 정합을 확인해야 합니다.

### 5.9 번역 왕복

tabbit의 `text` 타깃은 수집 방향만 있습니다. Luban은 번역표를 다시 읽어 **언어별 데이터
파일을 산출**하고, 수집 시점에 **키의 유효성을 검증**합니다.

**가치** — 번역 누락이 변환에서 검출되고, 언어별 산출물이 도구 안에서 산출됩니다. 다만
[행 벌](../spec/layout/table-row-sets.md)이 지역별 데이터를 담당하도록 이미 설계되어 있어 목적이 겹칩니다.

**부담** — 번역표를 소스로 읽는 경로가 필요하고, 그 자리는 §5.6과 같습니다. **순서상 행 벌
구현 이후에 판단할 항목입니다** — 그쪽이 먼저 들어오면 이 항목의 필요 범위가 축소됩니다.

### 5.10 편의 항목

|항목|가치|부담|
|--|--|--|
|`--watch`|개발 루프의 편의. 변환 시간이 짧은 프로젝트에서 효과가 큽니다|CLI 옵션과 재실행 루프. **원자적 교체와의 상호작용을 확인해야 합니다** — 파일이 교체되는 중에 다음 변환이 시작되는 경우입니다|
|enum 라벨 조합 표기|비트 위치를 모르고도 플래그를 기재할 수 있습니다|`bitset`과의 경계 결정이 선행입니다. 지금은 `bitset`이 비트 패턴만 받고 라벨은 enum 쪽에 있습니다|
|외부 타입 매핑|엔진 타입을 그대로 사용할 수 있습니다|언어마다 매핑 선언과 변환 코드. **생성 코드가 자립한다는 전제와 충돌합니다** — 매핑된 타입은 소비자 쪽에 있어야 합니다|
|set · map 컨테이너|테이블 참조로 대체되는 경우가 많아 가치가 낮습니다|배열과 별개의 와이어 표현이 필요합니다|
|protobuf · FlatBuffers 스키마 산출|미지원 언어와 기존 파이프라인의 연결|지원 언어가 이미 넓어 가치가 낮습니다|
|필드 변종|지역 · 버전별 값 컬럼을 필드 1개로|[행 벌](../spec/layout/table-row-sets.md)과 목적이 겹칩니다. 그쪽 구현 이후에 판단합니다|

## 6. 도입하지 않는 것

Luban에 있으나 이 저장소가 **이미 판단을 기록해 둔** 항목입니다. 재검토 대상이 아니라는
뜻으로 기재합니다.

|Luban의 기능|tabbit의 판단|근거|
|--|--|--|
|외부 어셈블리 플러그인|하지 않습니다 — 버전 간 안정된 계약의 비용이 이득보다 큽니다|[로드맵](../doc/roadmap.md)|
|사용자 템플릿 디렉터리|하지 않습니다 — 템플릿을 임베드로 두는 것이 「출하되는 것이 커밋된 것과 어긋나지 않게」 하는 장치이고 골든 게이트의 전제입니다. `text` 타깃만 예외로 열려 있습니다|`TemplateEngine`|
|다른 언어의 JSON 읽기|하지 않습니다 — 바이너리가 런타임 형식입니다|[로드맵](../doc/roadmap.md)|
|XML 스키마 정의 파일|하지 않습니다 — 시트가 스키마입니다. 정의를 두 곳에 두는 비용이 이득보다 큽니다|이 문서|

**참고 1건** — Luban의 이름 표기 설정은 6축(namespace · type · method · property · field ·
enum item)을 타깃별 옵션으로 지정합니다. [이름 표기 규약](../spec/targets/naming-conventions.md) §5는
`MemberCase` 1축이고 상수 · enum 라벨 · 타입 이름을 명시적으로 범위 밖에 두었습니다. 그 판단을
변경할 근거는 아니지만, **다른 도구에서 6축이 요구되었다는 사실은 확장 시점의 참고가 됩니다.**
