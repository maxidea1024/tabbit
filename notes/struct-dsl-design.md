# Tabbit STRUCT DSL 설계

> **문서 세트 밖의 정리 노트입니다.** 채택되면 `spec/`으로 옮깁니다.
> 도입 판단과 그 근거는 [STRUCT DSL 제안 검토](struct-dsl-review.md)에 있고, 이 문서는
> **그 검토가 확정한 범위 위에서 문법을 정하는 것**입니다.
>
> **목표는 Luban의 bean 정의 능력과 대등해지는 것입니다.** 그래서 §2를 항목별 대조표로 두어
> 「대등한가」가 눈으로 판정되게 했습니다. 조사 대상은 Luban 공식 문서이고, 근거 링크는
> §12에 있습니다.
>
> **초판이 합성 값 타입을 「없음」으로 적었는데 그것이 틀렸습니다.** `vec3f` · `quat` · `color`
> 계열은 브랜치 `worktree-vector-color-types`에 **설계와 구현이 끝나 있습니다**(`spec/composite-value-types.md`).
> **main에 병합되지 않았고 원격에도 없습니다.** 그 개정이 이 설계의 §7.3을 대부분 미리 만들어
> 두었으므로, 해당 절을 다시 썼습니다.

## 1. 범위 — 다시 확인

|무엇을|어디가 선언하는가|
|--|--|
|테이블 · 컬럼 · 인덱스 · target-side · 와이어 태그|**시트.** 지금 그대로|
|**임베딩 오브젝트(`struct`)의 이름과 멤버**|**DSL**|
|**enum**|**DSL.** 시트의 enum 엔티티도 남지만 **struct 멤버의 타입은 될 수 없습니다**(§4.4)|
|멤버의 제약|**양쪽.** 타입의 제약은 DSL, 그 컬럼만의 제약은 시트(§6.3)|

**멤버의 타입에는 이 도구의 기존 타입을 전부 사용합니다.** DSL이 타입 계열을 새로 만들지
않습니다.

## 2. Luban bean 대조 — 능력 단위로

**「있음」은 이 설계가 담는다는 뜻이고, 「하지 않음」은 판단이 이미 기록되어 있다는 뜻입니다.**

### 2.1 bean 자체

|Luban|표기|이 설계|
|--|--|--|
|이름|`<bean name="Item">`|`struct Item`|
|설명|`comment="…"`|`/// …` (§5)|
|상속 · 다형|중첩 `<bean>` · `parent`|`abstract struct` · `extends` — **문법은 예약하되 와이어 확인 뒤에 확정합니다**(§8)|
|**한 셀 압축**|`sep=","`|**`struct Reward (sep=",")`** — **기구는 이미 있습니다.** 합성 값 타입이 「셀 표기로 읽고 파싱 후 레코드로 접기」를 구현해 두었고, 이 항목은 그것을 **사용자 정의 struct로 일반화하는 것**입니다(§7.3)|
|외부 타입 매핑|`externaltype="unity_color"`|**하지 않습니다** — [기록된 판단](luban-comparison.md#510-편의-항목). 생성 코드가 자립한다는 전제와 충돌합니다|
|자유 메타데이터|`tags="k=v#k2=v2"`|괄호 메타데이터의 미지정 키(§6.4)|

### 2.2 필드

|Luban|표기|이 설계|
|--|--|--|
|이름 · 타입|`<var name="x" type="int"/>`|`field x int`|
|설명|`comment="…"`|`/// …`|
|참조 — 해석까지|(없음. Luban은 검사만)|`field itemId foreign Item` — **접근자까지 냅니다.** tabbit이 넓습니다|
|참조 — 검사만|`type="int#ref=item.TbItem"`|`field itemId int (refs=Item)`|
|다중 대상 참조|`ref=` 에 refgroup|`foreign Item\|CEquip` 또는 `(refs="Item\|CEquip")`|
|자원 경로|`#path=unity`|`field icon string (asset=icon)` — 종류별 루트는 recipe|
|번역 대상|`type="text"`|`field name string (text)`|
|산출 그룹|`group="s"`|**시트에 남습니다** — target-side는 레코드 단위로 이미 강제됩니다|
|기본값 금지|`type="int!"`|`(notDefault)`|
|범위|`#range=[1,100]`|`(min=1, max=100)` — 이름은 tabbit의 `Minimum` · `Maximum`을 따릅니다|
|허용값|`#set=1;2;3`|`(allowed=1;2;3)`|
|정규식|`#regex=^[a-z]+$`|`(regex="^[a-z]+$")`|
|컨테이너 길이|`(list#size=4),int`|`(size=4)` — **배열에 붙습니다**|
|원소 유일성|`(list#index=id),Foo`|`(uniqueBy=id)` — **배열에 붙습니다.** `index`라는 이름은 tabbit에서 테이블 인덱스이므로 쓰지 않습니다|
|nullable|`int?`|`int?` · `int[]?` · `int?[]` · `int?[]?` — **tabbit이 넓습니다**|
|필드 자유 태그|`tag="a=b"`|괄호의 미지정 키|

### 2.3 enum

|Luban|표기|이 설계|
|--|--|--|
|이름 · 설명|`name` · `comment`|`enum Element` · `///`|
|항목과 정수값|`<var name="RED" value="1"/>`|`value Red = 1`|
|항목 설명|`comment`|`///`|
|**별칭**|`alias="红"`|`(alias="빨강")` — **tabbit에 없던 것입니다.** [Luban 대조 §4.2](luban-comparison.md)의 「라벨 조합 표기」와 같은 자리|
|플래그 enum|`flags=1`|**하지 않습니다** — [`bitset` 타입](../spec/bitset.md)이 그 자리입니다|
|값 유일성|`unique`|기본으로 강제. 끄지 않습니다|
|외부 타입|`externaltype`|하지 않습니다|

### 2.4 타입 계열 — 대등하지 않은 것

|Luban|tabbit|판정|
|--|--|--|
|`byte` · `short` · `fshort` · `fint` · `flong`|없음|**대등하지 않습니다.** 크기 목적은 [컬럼 인코딩](../spec/tcb-v105-bit-width-packing.md)이 대체하나 **생성 코드의 타입을 좁히는 목적은 대체되지 않습니다.** DSL과 무관한 별건입니다|
|`bytes`|없음|같습니다|
|`vector2` · `vector3` · `vector4`|**`vec2i` · `vec3i` · `vec4i` · `vec2f` · `vec3f` · `vec4f`**|**있습니다**(미병합 브랜치). 성분 타입을 이름에 적으므로 Luban보다 좁게 선언됩니다|
|—|**`euler` · `quat` · `axisangle` · `color` · `color32`**, 그리고 색 팔레트와 `#3366CC` · `red` 표기|**tabbit만.** 이 영역은 이미 Luban보다 넓습니다|
|`set` · `map`|**지원 예정**|`set<T>` · `map<K,V>`. **형식은 움직이지 않습니다** — `set`은 배열 컬럼 하나, `map`은 키 · 값 컬럼 둘입니다(§4.7)|
|`array` · `list`|배열 2종|있음|
|—|`bigint` · `timespan` · `uuid` · `bitset`|**tabbit만**|

## 3. 설계의 축 — 세 채널

문법이 커지는 것은 **같은 것을 적는 방법이 둘 이상 생길 때**입니다. 그래서 적는 자리를
성질로 나누고, 그 경계를 넘지 않습니다.

|채널|무엇을|형태|
|--|--|--|
|`///`|**사람이 읽는 설명**|여러 줄 가능. 바로 다음 선언에 붙습니다|
|`=`|**값**|기본값과 enum 정수값. 그 둘뿐입니다|
|`( … )`|**기계가 읽는 메타데이터**|플래그와 키=값|

**이 경계가 제안의 `comment="level"`을 받지 않는 이유입니다.** 설명은 `///` 하나로 적습니다 —
여러 줄이 필요하고, 길어지면 한 줄이 넘치며, 넘치는 순간 이 DSL을 도입한 이유(편집 표면)가
사라집니다. `comment=`는 **오류로 하고 메시지가 `///`를 안내합니다.**

**괄호를 고른 것은 좋은 선택입니다.** 이 저장소에 이미 같은 형태가 있습니다 —
`LayoutOptions`의 자유 키/값 맵입니다. 코어가 키를 모르고, 소비하는 쪽이 읽고,
`RequireKnownOptions`가 오타를 보고합니다. **메타데이터의 정책을 새로 정할 필요 없이 그
정책을 그대로 씁니다**(§6.4).

## 4. 문법

### 4.1 예제

```
/// 3차원 좌표.
/// 한 셀에 `1,2,3` 으로 적을 수 있습니다.
struct Vector3 (sep=",")
    /// X 성분.
    field x float@1
    field y float@2
    field z float@3

/// 속성.
enum Element
    value Fire  = 1 (alias="불")
    value Ice   = 2 (alias="얼음")
    value Light = 3 (alias="빛")

/// 지급물 한 건.
struct Reward
    /// 지급할 아이템. 없는 id는 변환에서 거부됩니다.
    field itemId foreign Item|CEquip
    field count  int (min=1, max=9999)
    /// 표시용 아이콘. `Assets` 루트 아래에 실재해야 합니다.
    field icon   string? (asset=icon)
    field note   string  (text)
    field grade  Element = Fire
```

들여쓰기는 **문법적 의미가 없습니다.** 위 예제의 들여쓰기는 전부 장식이고, 없어도 같은
뜻입니다.

### 4.2 EBNF

```ebnf
file          = { line } ;
line          = doc-comment | declaration | comment | blank ;

declaration   = struct-decl | field-decl | enum-decl | value-decl ;

struct-decl   = [ "abstract" ] "struct" ident [ "extends" ident ] [ meta ] EOL ;
field-decl    = "field" ident type [ wtag ] [ "=" literal ] [ meta ] EOL ;
enum-decl     = "enum" ident [ meta ] EOL ;
value-decl    = "value" ident [ "=" int-literal ] [ meta ] EOL ;

wtag          = "@" positive-int ;

type          = element [ "?" ] [ "[]" [ "?" ] ] ;
element       = builtin-name
              | dsl-type-name
              | "foreign" table-name { "|" table-name } ;

meta          = "(" [ entry { "," entry } ] ")" ;
entry         = ident [ "=" meta-value ] ;
meta-value    = string | bare ;
bare          = ? `,` `)` 와 공백을 포함하지 않는 문자열 ? ;

literal       = number | string | "true" | "false" | ident ;

doc-comment   = "///" ? 줄 끝까지 ? ;
comment       = "//" ? 줄 끝까지 ? | "/*" ? … ? "*/" ;
```

**모호함이 없는 근거 3가지입니다.**

- **줄의 종류를 첫 낱말이 정합니다.** `struct` · `abstract` · `field` · `enum` · `value`
  5가지이고, 그 밖의 첫 낱말은 오류입니다. 파서는 앞을 볼 필요가 없습니다.
- **타입 뒤의 `(`는 언제나 메타데이터입니다.** `asset(icon)` 같은 타입 인자를 두지 않았기
  때문입니다 — 자원 종류는 `(asset=icon)`으로 적습니다. 이것이 **시트 표기보다 오히려 모델에
  가깝습니다**: [`StringRole`](../src/Models/StringRole.cs)에서 `text` · `asset`은 타입이
  아니라 `string`에 붙는 **역할**입니다.
- **메타 값에 `,`가 들어가면 따옴표로 감쌉니다.** `(regex="^a,b$")`. 규칙 하나로 끝나고
  렉서에 상태가 생기지 않습니다.

### 4.3 키워드

`struct` · `abstract` · `extends` · `field` · `enum` · `value` · `foreign` — **7개입니다.**
`set` · `map`은 키워드가 아니라 타입 이름입니다(§4.7).

### 4.4 타입 이름의 해석 범위

**멤버의 타입은 내장 타입과 이 DSL이 정의한 타입뿐입니다.** 시트가 선언한 enum은 멤버의
타입이 될 수 없습니다.

|무엇|멤버 타입으로|
|--|--|
|내장 타입 — `int` · `string` · `float` · `datetime` · `bitset` …|**됩니다**|
|**합성 값 타입** — `vec3f` · `quat` · `color` · `color32` …|**됩니다**(§4.8). 미병합 브랜치가 선행입니다|
|DSL의 `struct` · `enum`|**됩니다**|
|**시트의 enum 엔티티**|**안 됩니다**|
|테이블 이름|**타입이 아닙니다.** `foreign`의 인자일 뿐입니다(아래)|

**가시성이 한 방향인 근거는 자립입니다.** `.tbs` 파일 집합만으로 타입이 닫혀야 파서 하나로
IDE가 성립합니다 — 시트를 읽어야 타입이 결정되면 편집기가 워크북을 열어야 하고, 그것이
[VS Code가 코어 파서를 공유한다](struct-dsl-review.md)는 전제를 무너뜨립니다. 반대 방향은
열어 둡니다. **시트의 타입 칸은 DSL이 정의한 struct와 enum을 쓸 수 있습니다** — 그렇지
않으면 DSL의 선언이 struct 안에서만 쓰이게 됩니다.

> **옮기는 비용이 생기는 자리 하나.** 시트 enum을 쓰던 컬럼이 struct 멤버가 되면 그 enum을
> DSL로 옮겨야 합니다. 옮기는 동안 같은 이름이 양쪽에 있게 되므로, **거부가 기본이고
> 「DSL이 정본, 시트는 일치 검사」를 한시적으로 허용**하는 것이 안전합니다.

#### `foreign`의 테이블 이름 — 규칙의 정정

[검토 §4.1](struct-dsl-review.md)에 「**DSL 파일은 테이블 이름을 한 번도 언급하지
않습니다**」라고 적었는데, 그 문장이 넓었습니다. 규칙의 목적은 **같은 것이 두 곳에서
정의되는 것을 막는 데** 있고, 참조 대상을 가리키는 것은 정의가 아닙니다. 정정합니다 —
**DSL은 테이블을 선언하지 않습니다. 가리키는 것은 됩니다.**

그 대가로 `foreign`의 인자는 `.tbs`만으로 검사되지 않습니다. **편집 시점에는 미해결로 두고,
변환 시점에 기존 참조 해석 단계가 판정합니다.** 타입은 닫혀 있고 참조 대상만 열려 있는
구조입니다.

### 4.5 와이어 태그 — `@N`

**시트의 [`@N`](../doc/sheets.md#와이어-태그-n)과 같은 것이고, 같은 규칙을 그대로
물려받습니다.** 이름은 **wtag**입니다 — 메타데이터의 `tag`은 자유 메타데이터이므로(§6.1)
그것과 섞이지 않게 부르는 이름을 따로 둡니다.

|규칙|내용|
|--|--|
|**안 달면**|**선언 순서대로 1, 2, 3 …** 입니다|
|전부 또는 전무|한 struct 안에서 전부 달거나 전부 안 답니다. 섞으면 오류입니다|
|1 이상, 유일|중복과 0 이하는 오류입니다|
|**지운 멤버의 자리**|`(removed)` 로 남깁니다. 시트의 `#이름@N`과 같은 묘비입니다|
|재사용 금지|한 번 데이터를 실은 wtag는 다른 멤버에 줄 수 없습니다. 옛 리더가 새 멤버를 옛 필드로 읽고도 성공합니다|

**선언 순서가 여기서만 의미를 가집니다.** §4.6의 전방 · 후방 참조는 순서와 무관한데,
**wtag를 안 달면 순서가 와이어를 정합니다.** 그래서 결과가 이렇게 갈립니다.

|무엇|wtag 없음|wtag 있음|
|--|--|--|
|끝에 멤버 추가|안전합니다|안전합니다|
|**가운데 삽입 · 삭제 · 줄 이동**|**뒤의 wtag가 전부 밀립니다.** 배포된 리더가 어긋나고, `sep` 셀의 성분 위치도 함께 어긋납니다|안전합니다|

**데이터를 한 번이라도 배포한 struct에는 wtag를 답니다.** 안 다는 것은 아직 배포 전인
struct의 편의입니다.

#### 와이어 컬럼을 여럿 만드는 멤버 — 미결

**wtag는 와이어 컬럼 하나에 대응하는 멤버에만 답니다.** 멤버의 타입이 struct이거나 합성 값
타입이면 그 멤버 하나가 **와이어 컬럼 N개**가 되고, 번호 하나로 N개를 가리킬 수 없습니다.

**합성 값 타입 개정이 같은 자리에서 같은 판단을 이미 했습니다.** 합성 컬럼은 `@N`을
거절하고, 그 이유를 이렇게 적어 두었습니다 — 「하나만 적힌 것을 N개로 늘리면 적지 않은
태그를 조용히 가져가게 됩니다. 태그를 쓰는 테이블은 성분을 컬럼으로 적습니다.」

그래서 갈립니다.

|시트 표기|leaf의 wtag를 누가 적는가|
|--|--|
|**(나)** 멤버 컬럼이 시트에 있음|**시트가 적습니다** — `Pos.X@3` · `Pos.Y@4`. 지금과 같고, DSL의 wtag가 관여하지 않습니다|
|**(다)** `sep` 한 셀|**멤버 컬럼이 시트에 없으므로 DSL이 적어야 합니다.** 그런데 struct는 자기가 어느 테이블의 몇 번인지 모릅니다|

**(다)에서 미결입니다.** 두 방향이 있고 값이 다릅니다.

|방향|내용|
|--|--|
|**태그를 경로로**|바깥 struct의 `pos@3`과 안쪽 `Vector3`의 `x@1`이 합쳐져 `3.1`이 됩니다. **안쪽 struct에 멤버를 더해도 바깥이 밀리지 않습니다** — 재사용되는 타입에 맞는 성질입니다. 대가는 **형식이 태그 경로를 담아야 한다는 것**이고, 별건의 개정입니다|
|**바깥이 연속 블록을 잡음**|`pos`가 태그 3개를 차지합니다. 형식은 그대로이나 **안쪽 struct에 멤버를 하나 더하면 그 타입을 쓰는 모든 바깥 struct의 뒤쪽 태그가 밀립니다.** 재사용을 전제한 타입에서 가장 나쁜 성질입니다|

**1차에서는 결정하지 않고 거절합니다** — `sep` struct에 struct · 합성 타입 멤버를 두는 것을
받지 않습니다. 스칼라 멤버만으로도 `Vector3` · `Reward` 같은 실제 쓰임이 덮이고, 위 선택은
**실제로 중첩이 필요해진 시점에** 그 요구를 보고 정하는 편이 낫습니다.

### 4.6 선언 순서 독립성

**전방 참조와 후방 참조가 모두 됩니다.** 파일 안에서도, 파일 사이에서도, 로드 순서와도
무관합니다.

```
struct Skill
    field effect Effect      // 아직 나오지 않은 타입

struct Effect
    field damage int
```

**새로 만들 단계가 아닙니다.** 테이블 참조가 이미 그렇게 해석됩니다 — 전부 수집한 뒤
[`Model.cs:395`](../src/Models/Model.cs#L395) 부근에서 이름을 찾고, 그 자리에서 순환도
거부합니다. DSL의 타입 해석은 그 단계에 얹습니다.

**§4.5와 상충하지 않습니다.** 순서가 무관한 것은 **해석**이고, wtag를 안 달았을 때 순서가
정하는 것은 **와이어**입니다. 같은 파일을 위아래로 옮겨 적어도 타입은 같게 해석되지만,
wtag가 없으면 나오는 파일이 달라집니다 — 그 둘이 다른 층이라는 것을 알고 있어야 하는
자리입니다.

### 4.7 컨테이너 — `set`과 `map`

**지원합니다.** 표기는 `set<T>` · `map<K,V>`이고, 배열과 조합됩니다 — `map<int,Reward>[]`.

> **꺾쇠를 고른 이유.** 대괄호는 배열 표기와 충돌합니다 — `map[int,Item][]`은 어느 쪽이
> 배열인지 눈으로 갈리지 않습니다. 이 DSL에는 비교 연산자가 없으므로 `<` `>`가 비어
> 있습니다.

#### 와이어 — 형식 무변경

**초판이 「와이어에 표현이 없어 형식 개정」이라고 적었는데 그것이 틀렸습니다.** 필요한 것이
이미 다 있습니다.

|무엇|어떻게 실리는가|
|--|--|
|`set<T>`|**`T[]`와 같습니다** — `KindVarArray` 컬럼 하나. 다른 것은 중복을 거부하는 검사와 생성 코드의 컨테이너 타입뿐입니다|
|`map<K,V>`|**컬럼 둘** — `Foo.Key`와 `Foo.Value`, 둘 다 `KindVarArray`이고 길이가 같습니다. **멤버가 2개인 레코드 배열과 완전히 같은 모양입니다**|

[중첩 필드](../spec/nested-fields.md#4-와이어--변경-없음)가 이미 증명한 「API는 AoS, 파일은
SoA」가 그대로 적용됩니다. **`.tcb` 버전도, 리더도 움직이지 않습니다.**

#### 결정해야 하는 것

|무엇|결정|
|--|--|
|**파일에 실리는 순서**|**시트에 적힌 순서 그대로.** 정렬하지 않습니다 — 언어마다 컨테이너의 순회 순서가 다르므로, 도구가 정렬하면 어느 언어의 순서를 고를지가 임의가 되고 골든이 그 임의값을 굳힙니다|
|**키 타입**|`int` · `bigint` · `string` · `enum`만. **`float` · `double`은 거부합니다**(동등성이 표현에 달립니다). struct 키도 거부합니다|
|**중복**|`set`의 원소 중복과 `map`의 키 중복은 **오류**입니다. 그 셀을 가리켜 보고합니다|
|**셀 표기**|`set`은 배열과 같습니다(`a;b;c`). `map`은 항목 사이가 배열 구분자, 키와 값 사이가 `:` — `1:sword;2:shield`. 값이 struct면 성분 구분자가 한 겹 더 필요하고, 그것은 [합성 값 타입](struct-dsl-review.md)의 `sep`과 같은 문제입니다|
|**옵셔널**|`map<K,V>?`는 배열의 `T[]?`와 같습니다. `map<K,V?>`(값이 없을 수 있는 map)는 **1차에서 담지 않습니다**|
|**map이 없는 언어**|C · Go의 일부 · Rust는 이미 참조에서 같은 갈래를 겪었습니다. 컬럼 2개와 조회 함수로 냅니다|

#### 비용의 실제 위치

**언어별 생성 코드입니다.** 형식이 안 움직이므로 남는 것은 모든 언어에 컨테이너 타입과 그
구축 코드를 내는 일이고, **[중첩 필드 확산](../spec/nested-fields.md)과 같은 모양의
작업입니다** — 언어를 하나씩, 컴파일과 되읽기 게이트를 각각. 익스포터 쪽은 `json`의 map
표현(키가 정수일 때의 문자열화)과 데이터베이스 쪽 매핑이 결정 사항입니다.

#### 이 설계에서 잡아 두는 것

**문법과 모델까지 받고, 그 뒤에서 이름과 함께 거절합니다.** 이 저장소가 이미 쓰는 방식이고
(레코드를 만난 `html` 타깃이 그렇게 합니다), 그러면 나중에 구현하는 쪽이 **문법을 다시
정하지 않고 거절하는 자리만 채웁니다.**

```
Target `csharp` does not support map columns yet.
  Table `Shop` field `Prices` is `map<int,int>`.
```

### 4.8 합성 값 타입을 멤버로

**됩니다. 그리고 새로 만들 것이 없습니다.**

```
struct Character
    field pos   vec3f
    field rot   quat
    field tint  color
```

확장하면 `Character.Pos.X` 같은 **중첩 레코드**이고, 그것은
[다중 중첩](../spec/nested-multi-level.md)이 이미 지원하는 모양입니다 — 로드맵 5a″가 「깊이를
지원한 것이 아니라 깊이를 세지 않게 만든 것」이라고 적은 그 자리입니다. **형식도 생성기도
움직이지 않습니다.**

합성 값 타입 개정도 같은 것을 반대편에서 확인해 두었습니다 — `Slot1.Pos: vec3f`가 「별도 작업
없이」 된다고 적혀 있고, 그 근거가 확장 결과가 「멤버가 레코드인 레코드의 배열」이라는
것입니다.

**그 개정의 제약을 그대로 물려받습니다.**

|물려받는 것|내용|
|--|--|
|**성분별 제약 거절**|`field pos vec3f (min=0)`은 받지 않습니다. 범위가 성분에 대한 것인지 크기에 대한 것인지 정해지지 않았습니다|
|**`?`의 presence 미기록**|`vec3f?`의 빈 칸과 빈 값을 적은 칸이 파일에서 구별되지 않습니다. 레코드 멤버가 nullable이 아니기 때문입니다|
|**`@N` 불가**|위의 미결 항목과 같은 문제입니다|

**새로 생기는 충돌이 하나 있습니다.** `sep`의 구분자와 합성 값의 성분 구분자가 **둘 다
쉼표**입니다. `struct Reward (sep=",")`에 `field pos vec3f` 멤버를 두면 한 셀이
`101,2,1.5,-2.5,0`이 되고, 위치로 풀 수는 있으나 사람이 읽을 수 없습니다.
**§4.5의 미결과 같은 이유로 1차에서 거절합니다** — 합성 값 타입 개정도 배열 구분자와의 같은
충돌을 「담는 날의 선행 조건」으로 적어 두었습니다.

**선행 조건은 병합입니다.** 이 절 전체가 미병합 브랜치 위에 서 있으므로 §11의 0단계에
걸립니다.

### 4.9 동적 배열 단일화 — `KindFixedArray`의 제거

**정적 개수 배열은 어디에도 없습니다.** DSL에도, 시트에도, 와이어에도 없습니다.

|무엇|결과|
|--|--|
|`field costs int[]`|길이는 **데이터가 정합니다**|
|**시트의 연번 컬럼** `Slot1` · `Slot2`|**컬럼 개수는 칸의 수일 뿐 배열의 길이가 아닙니다.** 이것도 가변으로 냅니다|
|와이어|**`KindVarArray` 하나만 남깁니다.** `KindFixedArray`를 형식에서 제거합니다|
|`(size=4)`|**길이 선언이 아니라 검사입니다.** 이름이 선언처럼 읽히므로 `sizeIs` · `maxSize`처럼 검사임이 드러나는 이름으로 바꾸는 것을 검토합니다|
|`sep` 한 셀|원소 개수가 셀마다 다릅니다. 개수를 미리 알 필요가 없습니다|

#### 제거의 근거 — 배포

길이가 **생성 코드에 상수로 구워집니다.** C#이라면 이렇고, 15개 템플릿이 전부 같은 것을
합니다.

```csharp
internal const int Slot_N = 2;
for (int j = 0; j < Record.Slot_N; ++j)      // 읽기 루프가 그 상수를 돕니다
```

**그래서 컬럼을 하나 더하는 것이 코드 재배포가 됩니다.** 배포된 리더는 자기가 아는 개수까지만
읽습니다. 이 도구가 매니페스트와 데이터 패치 업데이터를 갖추고 「데이터만 배포할지 코드까지
배포할지」를 판정하는 것과 어긋나는 자리이고, **와이어 태그가 존재하는 이유와 같은 종류의
문제입니다** — 신원과 개수가 코드에 굳어 있으면 데이터만으로 바꿀 수 없습니다.

#### 비용 — 컬럼당 한 런

> **인코더를 읽은 결과이고 실행해서 잰 것이 아닙니다.**
> [`TcbColumnEncoder.EncodeArray`](../src/Exporters/TcbColumnEncoder.cs#L300)

가변 배열이 되면 길이 스트림이 붙습니다. 그런데 그 스트림도 **다른 컬럼과 똑같이
인코딩됩니다** — raw varint 또는 RLE 중 작은 쪽입니다. 그 코드의 주석이 이미 답을 적어
두었습니다.

> 「A column whose rows are all the same length, **which is most of them, becomes one run**」

즉 모든 로우의 길이가 같은 컬럼은 **런 하나**입니다. 로우 수와 무관하게 **컬럼당 몇
바이트**이고, 로우마다 붙는 비용이 아닙니다. 대신 디스크립터에서 개수 필드가 사라지므로
그만큼 돌려받습니다.

#### 파급 범위

**예약하지 않고 지웁니다.** 부담은 한 번에 집니다.

|  |내용|
|--|--|
|**형식**|kind 1을 **삭제하고 정리합니다** — `KindScalar = 0` · `KindArray = 1`. 배열이 하나뿐이므로 `Var`라는 수식도 뜻을 잃습니다. 버전 **106 → 107**|
|**번호 예약이 필요 없는 근거**|리더가 버전을 **정확 일치로 검사하고 다른 버전을 거부합니다**([`TcbReader.cs:1507`](../lib/cs/tabbit/TcbReader.cs#L1507)). 번호 예약은 「옛 리더가 새 파일을 옛 뜻으로 읽고도 성공하는 것」을 막는 장치인데, **버전 게이트가 이미 막습니다.** 형식 주석이 「103이 움직인 이유」로 적어 둔 것이 바로 이 구분입니다 — 거부하면 버전을 올리고, 잘못 읽으면 문제입니다|
|**리더 호환**|**옛 리더는 거부합니다.** 런타임이 생성 코드와 함께 나가므로 같이 움직이고, 그것이 이 변경에서 한 번 지는 부담입니다|
|**생성 코드**|`_N`이 15개 언어에서 사라집니다. 길이를 읽어 할당하고 그만큼 도는 **가변 경로가 이미 모든 언어에 있으므로**, 고정 경로를 그쪽으로 수렴시키고 죽은 분기를 지우는 일입니다|
|**`.tcb`**|**움직입니다.** 골든 전량 재기록이고 그 diff가 리뷰 대상입니다|
|**`TrimTrailingArrayElements`**|뜻이 바뀝니다. 「고정인가 가변인가」가 아니라 「**빈 뒤쪽 칸을 적은 것으로 볼 것인가**」만 남습니다. 옵션 자체는 유지됩니다|

**판정 기준은 되읽기입니다.** 형식이 바뀌므로 바이트 동일은 기준이 될 수 없고, **모든 언어가
새 파일을 읽어 값이 이전과 같은지**가 기준입니다. 적합성 코퍼스가 그 자리입니다.

> **두 번 정정한 자리입니다.** 처음에는 「`.tcb`가 한 바이트도 움직이지 않아야 한다」고
> 적었는데 그것은 형식을 두고 생성 코드만 고치는 경우의 기준이었고, 다음에는 「소비 측
> 코드 변경 없이 읽힌다」고 적었는데 **버전이 올라가면 옛 리더는 거부합니다.** 형식을
> 건드리는 변경이므로 런타임도 함께 나갑니다.

## 5. 설명 — `///`

|규칙|내용|
|--|--|
|붙는 대상|**바로 다음 선언.** 들여쓰기는 관여하지 않습니다|
|여러 줄|연속한 `///` 줄이 한 덩어리입니다. `/** */`는 **두지 않습니다** — 같은 것을 적는 두 번째 방법이기 때문입니다|

**멤버 컬럼의 설명 칸을 어떻게 할 것인가**는 §6.3과 같은 규칙으로 처리합니다.

### 6.1 키 목록

|`notDefault`|플래그|스칼라 · **원소**|없음 → [§5.8](luban-comparison.md#58-시트에-기재하는-제약의-확대)|

|`tag`|자유 문자열|무엇이든|**wtag가 아닙니다.** Luban의 `tag=`에 대응하는 자유 메타데이터입니다|

### 6.2 배열과 원소를 가르는 방법

**키 이름 하나는 붙는 자리 하나에만 대응합니다.** 두 자리에 걸리는 키를 만들지 않으므로
접두사(`element.`)가 필요 없습니다.

```
field costs int[] (min=1, size=3)
                   ~~~~~  ~~~~~~
                   원소    배열
```

Luban은 이것을 `(list#size=4),int#range=[1,]`처럼 **타입 안쪽에** 적어 구분합니다. 이 설계는
**이름으로** 구분합니다 — 타입 표기가 단순해지는 대신, **새 키를 추가할 때 「이 키가 어느
자리인가」를 반드시 이 표에 적어야 합니다.** 그것이 이 선택의 유지 비용입니다.

### 6.3 타입의 제약과 그 컬럼의 제약

같은 struct가 여러 테이블에서 쓰이므로 제약도 두 층이 됩니다.

|어디에 적힌 것|뜻|
|--|--|
|**DSL**|**그 타입이면 언제나** 만족해야 하는 것|
|**시트의 제약 행**|**그 컬럼에서만** 추가로 만족해야 하는 것|

**둘 다 있으면 둘 다 만족해야 합니다(교집합).** 완화가 아니라 강화만 가능하다는 뜻이고,
이렇게 두면 **DSL만 읽고도 「최소한 이것은 보장된다」가 성립합니다.** 우선순위 규칙을
새로 만들 필요가 없습니다.

> 시트가 DSL의 제약을 **완화**하도록 두면, 타입의 제약이 아무것도 보장하지 않게 됩니다.
> 그러면 §6.1의 표 전체가 문서 주석과 같은 값이 됩니다.

### 6.4 모르는 키

**`LayoutOptions`와 같은 정책입니다.** 파서는 키를 검증하지 않고 그대로 맵에 담습니다.
소비하는 쪽(모델 조립 단계)이 아는 키를 읽고, **`RequireKnownOptions`에 해당하는 검사가
나머지를 오타로 보고합니다.** 자유 태그를 쓰려면 그 검사에서 빠지는 접두사를 하나 정합니다
— 예: `x.` 로 시작하는 키는 검사하지 않습니다.

### 6.5 `key`를 두지 않는 이유

제안 예시의 `key` 플래그는 두 가지로 읽힙니다 — 배열 원소의 유일성 키이거나, map의 키입니다.
map은 없으므로 앞의 것인데, **그 성질은 타입이 아니라 사용처에 있습니다.** 같은 `Reward`가
배열이 아닌 자리에도 쓰이면 그 멤버의 `key`는 뜻할 것이 없습니다. 그래서 **배열 쪽에
`uniqueBy=id`로 적습니다** — Luban이 `index`를 컨테이너에 두는 것과 같은 판단입니다.

## 7. 시트와의 결합

### 7.1 세 가지 표기와 그 와이어의 동일성

`Reward`를 3개 담는 컬럼 그룹의 세 표기입니다.

|  |시트|컬럼 수|헤더 기재|
|--|--|--|--|
|**(가)** 지금 그대로|`Reward1.ItemId` `Reward1.Count` …|**9**|멤버마다 타입 · 설명을 적습니다|
|**(나)** 타입 이름만|같은 컬럼, **타입 칸은 그룹에 `Reward` 하나**|**9**|**반복이 사라집니다**|
|**(다)** 한 셀 압축|`Reward1` `Reward2` `Reward3`, 셀에 `101,2,아이콘`|**3**|없습니다|

**셋 다 와이어가 동일합니다.** 레코드는 원래 [멤버마다 한 컬럼](../spec/nested-fields.md)으로
실리므로, 달라지는 것은 **읽는 방법뿐이고 형식도 생성 코드도 그대로입니다.**

**(나)를 기본으로, (다)를 옵트인으로 권고합니다.**

### 7.2 (나) — 반복 기재의 제거

멤버 컬럼의 타입 칸과 설명 칸을 비우고, 그룹의 타입 칸에 struct 이름만 적습니다.
칸이 채워져 있으면 **DSL과 일치하는지 검사하고, 어긋나면 거부합니다** — 기존 시트가 그대로
통과하면서 새 표기로 옮겨갈 수 있게 하는 자리입니다.

**「엑셀 컬럼만 봐도 데이터 구조를 이해할 수 있다」는 유지됩니다.** 컬럼 이름
(`Reward1.ItemId`)이 그대로 남기 때문입니다.

### 7.3 (다) — `sep`, 합성 값 타입의 일반화

**새 기구가 아닙니다.** 미병합 브랜치의 [합성 값 타입](https://github.com/maxidea1024/tabbit)
개정이 「셀 표기로 읽고 **파싱이 끝나면 레코드로 접는다**」를 이미 구현해 두었고, 확장 패스가
쿠커에 있습니다(`ModelCooker.Composites.cs`). 이 항목은 그 기구의 대상을 **내장 7종에서
사용자 정의 struct로 넓히는 것**입니다.

```
Reward1              Reward2
101,2,icon_a         205,1,icon_b
```

**그 개정이 이미 결정해 둔 것을 그대로 물려받습니다.**

|무엇|그 개정의 결정|
|--|--|
|성분 구분자|**쉼표 고정.** 괄호는 생략 가능|
|성분 개수|**정확히 일치.** 줄이거나 늘려 받지 않습니다|
|접히는 시점|확장 직후. **와이어 · 모든 생성기 · 익스포터 · 이력은 레코드만 봅니다**|
|동치 증명|같은 데이터를 두 표기로 적은 픽스처 2벌의 `.tcb`가 **바이트 동일**입니다|

**그리고 그 개정이 담지 않기로 한 것도 함께 물려받습니다 — 이것이 초판의 예시를 무르는
자리입니다.**

|담지 않는 것|이 설계에 미치는 것|
|--|--|
|**한 셀의 가변 배열**(`vec2f[]`)|초판이 예시로 든 `101,2,a;205,1,b`는 **지금 담지 않는 모양입니다.** 고정 개수는 `Reward1` · `Reward2` 컬럼으로 적습니다|
|**배열 구분자와의 충돌**|`ArrayDelimiter`가 쉼표인 소스에서는 원소 경계와 성분 경계가 같은 문자가 됩니다. **한 셀 배열을 담는 날의 선행 조건입니다**|
|**성분별 컬럼 제약**|`min` · `max`가 성분에 대한 것인지 크기에 대한 것인지 갈리므로 **지금은 거절합니다.** §6.1의 제약 키를 `sep` struct에 붙일 때 같은 질문이 그대로 나옵니다|
|**합성 컬럼의 존재 비트**|레코드 멤버는 nullable이 아니므로, 빈 칸과 빈 값을 적은 칸이 파일에서 구별되지 않습니다|

**남는 비용 2가지입니다.**

|  |내용|
|--|--|
|**셀 안이 위치 기반**|멤버를 가운데 추가하면 **기존 셀이 전부 어긋납니다.** §4.5의 wtag와 같은 뿌리입니다|
|**히스토리가 셀 단위**|멤버 하나만 고쳐도 그 셀 전체가 변경으로 기록됩니다|

초판이 「오류 위치를 셀 안쪽까지 보고해야 한다」를 실제 구현 비용으로 적었는데, **그 개정이
이미 그 진단들을 냅니다**(성분 개수 불일치 · 접두 불일치 · 서식 지목). 사용자 정의 struct로
넓힐 때 새로 만들 것이 아니라 그 자리를 넓히는 일입니다.

**그래서 옵트인입니다.** 멤버가 적고 값이 짧은 struct에서 이득이 크고, 멤버가 많거나 문자열이
긴 struct에서는 (나)가 낫습니다.

### 7.4 recipe

DSL 파일의 자리를 recipe가 지정하고, **[빌드 캐시](../spec/build-cache.md)의 입력에
포함해야 합니다.** 넣지 않으면 스키마만 바뀐 변환이 캐시에 적중합니다.

```jsonc
"Schemas": [{ "Path": "./schemas" }]
```

## 8. 다형 — 문법의 예약

```
abstract struct Effect
struct DamageEffect extends Effect
    field damage int
struct HealEffect extends Effect
    field amount int
```

**이 문법은 지금 확정하지 않습니다.** [검토 §5](struct-dsl-review.md)의 결론대로 **와이어
설계의 성립 여부가 먼저**이고, 그전에 `abstract` · `extends`를 확정하면 성립하지 않았을 때
지울 수 없는 문법이 남습니다. 그때까지 다형은 [다중 대상 참조](../spec/multi-target-accessors.md)로
표현합니다 — 판별자와 변종별 접근자가 모든 언어에 이미 있습니다.

확정할 때 함께 정해야 하는 것이 3가지입니다 — **기반 struct에 필드를 둘 수 있는가**(상속이
없는 언어에서 복제됩니다), **판별자 값을 무엇이 정하는가**(§4.5의 wtag와 같은 문제입니다), **시트의 `$type` 컬럼
표기**입니다.

## 9. 남은 결정

### 9.1 struct · enum · 테이블의 이름 공간

같은 이름 공간인지, 그리고 DSL의 식별자가
[이름 표기 규약](../spec/naming-conventions.md)과 `NamingRules`를 통과하는지를 정해야
생성 코드가 일관됩니다.

### 9.2 순환

**struct 그래프는 DAG여야 합니다.** 값으로 임베드되는 struct의 순환은 컬럼으로 펼칠 수
없습니다 — `A.b.a.b…`가 끝나지 않습니다. 순환이 필요한 관계는 참조(`foreign`)이고, 이미
그렇게 갈려 있습니다.

### 9.3 소속의 암묵 결합

`field`는 **직전 `struct`에 붙습니다.** 들여쓰기가 의미를 갖지 않으므로 소속을 나타내는
것은 순서뿐이고, `struct` 줄에 오타가 있으면 그 필드들이 말없이 앞 struct로 편입됩니다.
**문법은 그대로 두고, 들여쓰기가 암묵 소속과 어긋나면 경고하는 린트**로 방지합니다.
